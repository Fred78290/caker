# Seamless Linux windows on the macOS desktop (WSLg-style)

Status: **feature complete, in review (PR #175).** The host side (Swift, `Sources/cakedlib/Seamless/`) and the guest compositor (C/wlroots, `seamlessd/` of the cakeagent repository) run together on real Ubuntu 26.04 arm64 Caker VMs over the real vsock bridge: `foot`, `gnome-terminal`, Files and the snap Firefox show up as native macOS windows, typed keys and the mouse wheel reach the guest, and the output is drawn back. It is wired into the VM lifecycle, works for a VM run by a `caked service` (gRPC tunnel), for every guest user (hub), from `cakectl sh`/`exec`/`seamless` and from Caker.app. The cakeagent that ships the compositor is released as **v1.0.326** (`CAKEAGENT_VERSION`), with the clipboard.

## Idea

WSLg runs Weston with an RDP backend in the guest; every Wayland window becomes an RDP RemoteApp window on the Windows host. Caker does the same without RDP: a compositor in the guest streams one pixel buffer per toplevel/popup over **vsock**, the host shows each in its own `NSWindow` and sends input back.

A custom virtio device (macOS 27) is *not* needed: vsock is upstream in every guest kernel, already attached by Caker, and fast enough for damage rectangles. A custom device would only matter later for zero-copy buffers or GPU acceleration, and it needs a guest kernel driver on every distro.

### Plumbing into a VM, no VM code changes

The existing socket device bridges guest-initiated vsock connections to a host unix socket:

```
connect://vsock:5100/<path to the seamless socket>
```

The guest compositor connects to vsock port `5100` (`SeamlessProtocol.defaultVsockPort`), the bridge in `VirtualSocketDevices.swift` forwards it to the socket `SeamlessServer` listens on.

## Protocol (version 5)

Frame: `u32 length` (type byte + payload) + `u8 type` + payload, little endian, strings `u16 length` + UTF-8. Types `0x01...0x7F` guest to host, `0x81...0xFF` host to guest. First message must be `hello`; the host answers `helloAck` with the output scale (`120` == 1x, fractional-scale units).

Guest to host: `hello`, `windowCreate` (id, parent, toplevel/popup, popup offset, title, app id), `windowTitle`, `windowAppID`, `windowHints` (min/max size), `windowFrame`, `windowDestroy`, `cursor` (CSS cursor name), `clipboard` (`0x09`, version 3).

Host to guest: `helloAck`, `output` (scale change), `windowResize` (logical size), `windowClose` (request, the guest answers `windowDestroy`), `windowFocus`, `pointerEnter/Leave/Motion/Button/Axis` (logical surface coordinates, evdev button codes; `Axis` carries a source: `continuous` trackpad pixels, `wheel` mouse notches reported to clients as discrete `value120` steps, `stop` when the fingers leave the trackpad. Version 2 added the source byte. The host still accepts a version 1 guest: it answers `helloAck` with the guest's version and never sends `Axis` to it, so such a guest works without the mouse wheel until its agent is updated; a guest newer than the host is refused), `key` (evdev code, delivered to the focused window).

`clipboard` (`0x09` guest to host, `0x8C` host to guest, version 3): `u8 format` (0, UTF-8 text) + `u32 length` + bytes, at most 1 MiB (`SeamlessProtocol.maxClipboardBytes`, `SEAMLESS_MAX_CLIPBOARD`). A guest on protocol 2 is accepted without it (the host never sends `clipboard` to it and logs that the clipboard is disabled until its agent is updated); a text with a broken UTF-8 sequence is decoded loosely rather than ending the session.

`windowFrame`: buffer size in pixels + damage rectangles. Pixels are BGRA premultiplied (`wl_shm` ARGB8888 on little endian). Each rectangle is raw or an LZ4 **raw block** (what `LZ4_compress_default` writes); the guest picks per rectangle. Buffer pixels = logical size * scale / 120.

The guest is untrusted: sizes, rectangle bounds, string lengths, floats and decompressed sizes are all validated, the host caps the windows (64), the frames in flight (8) and a buffer at 40 Mpx, the socket is `0600`, and every title is prefixed `[<vm>]` so a guest cannot pass its windows off as a host application's.

## Wired into the VM lifecycle

- **Per VM option** `CakeConfig.seamless` (`config.json`, Linux guests only): `caked build/launch --seamless` (set at build time, which is what makes the cloud-init seed install the compositor), `caked configure <vm> --seamless true`, `cakectl configure` (new `ConfigureRequest.seamless`, `Configuration.seamless` in `service.proto`), a "Seamless windows" toggle in Caker's VM settings and in the VM creation wizard (Options, Linux images only; it must be chosen at creation, see above).
- **Socket device**: `CakeConfig.socketDeviceAttachments(agentURL:seamlessSocketURL:)` adds `connect://vsock:5100/<vm dir>/smls`. The path is `VMLocation.seamlessSocketURL` (`<vm dir>/smls`, through the same `socketPath(name:)` helper as the agent and service sockets, which falls back to a short temporary path when the VM path is too long for a `sockaddr_un`; that fallback is logged at debug level, since the longer `smls` name triggers it routinely): the socket device, `VirtualMachine.startSeamlessWindows()` and the `SeamlessTunnel` all take it from the VM's location, so they can't disagree (it used to be `CakeConfig.seamlessSocketPath`, a name of its own computed from the configuration).
- **Server**: `VirtualMachine.startSeamlessWindows()` starts a `SeamlessWindowManager` once the VM runs, in any process that runs the VM: Caker.app and `caked vmrun --ui`/`--all` have an application already, a `vmrun --vnc` (what a background start uses) gets an accessory one from the manager (`SeamlessWindowManager.prepareApplication`, no Dock icon or menu bar) and `VMRun` runs its event loop after setting the activation policy to `.prohibited` (`561bfc76`: windows are composited individually, so the host process shows no Dock icon at all, not even an accessory one; only in this seamless branch, a `vmrun --vnc` without seamless doesn't touch the policy, since an application would take focus away from the terminal), and a new guest toplevel activates it so the window comes forward (not re-checked under `.prohibited`). A VM run by the caked service doesn't listen (see `SeamlessTunnel` below). `didChangedStateOnStop` stops it and removes the socket.
- **Guest**: `CakeConfig.agentServiceFlags` adds `--seamless --seamless-user=<vm user> --seamless-layout=<host layout>` to `cakeagent service install` in both install scripts (cloud-init and SSH), so a freshly built VM, or an agent update, installs the compositor service. The host keyboard layout comes from `SeamlessKeyboardLayout` (macOS input source id to XKB layout, plain layouts only).
- **`caked shell`/`exec` auto-start**: a VM they start in the background (`StartHandler`, `.background`) runs plain `caked vmrun --vnc`: for a seamless VM `VMRun` runs an accessory `NSApplication` (instead of waiting on the stop promise) so the headless process can draw the guest's windows, and exits with the VM like any other. Verified: windows owned by that process, socket, PID file and windows gone after `caked stop`. Not verified: that the window really comes to front (the Mac was at the login window during the check).
- **Shell and commands run as the seamless user**: the agent runs as root, whose runtime directory (`/run/user/0`) holds no compositor socket, so a root shell or command could never open a window. `ExecuteRequest` carries a `user` (`Shell.user`, `Command.user` in `agent.proto`); the VM's configured user (`CakeConfig.configuredUser`, or `--user <name>` on `caked`/`cakectl` `sh`/`exec`) is what `caked shell`/`exec`, the gRPC relay (`CakeAgentConnection.execute`) and the GUI terminal (`ShellCakeAgent`) send. A root Linux agent then runs the process with that user's credentials, groups, `HOME`/`USER`/`SHELL`, terminal ownership and `XDG_RUNTIME_DIR`, plus the display variables when the compositor runs (a command doesn't source the login profile). An empty user keeps the agent's own, a non-root agent refuses another user, the macOS agent ignores it. **`exec`/`sh` therefore no longer run as root by default, in any Linux VM** (the default is the configured user, not only for seamless VMs): pass `--user root` or use `sudo`. Needs the cakeagent with this (snapshot `93f70116`, Fred78290/cakeagent#27). Starting an app in the first seconds after boot can still lose a race with the compositor/activation environment (the D-Bus activated service then fails with \"Cannot open display\" until `systemctl --user reset-failed`).
- **Every guest user can have windows** (the agent's `Hub`, `pkg/seamless/hub.go` in the cakeagent repository; no change to the host, the tunnel or the wire format). The host accepts one compositor per VM (a new connection replaces the previous), so each user's `caker-seamlessd` connects to a unix socket of the agent (`/run/caker-seamless/hub.sock`, `--connect unix:`) instead of the vsock port, and the agent keeps the one vsock connection to the host. The kernel tells who is on the other end (`SO_PEERCRED`; root is refused). The hub does the hello exchange with the host once and answers each compositor's own, puts the compositor's slot (1...255) in the top byte of every window id (so ids of different users can't collide, and a compositor can't name another one's windows: ids that already carry slot bits are a protocol error), routes input back by that byte, and sends keys to the compositor that owns the focused window. When a compositor goes away the hub destroys its windows on the host, the host connection closes with the last compositor, and the compositors dial again if the host goes away. A user other than the configured one (`--seamless-user`, `CakeConfig.seamlessUser`) gets `<user>: ` in front of its window titles, after the host's `[vm] `. The `--seamless-user` compositor is still started with the agent; **any other user's compositor starts on demand**, when `caked sh/exec --user <name>` (or the GUI terminal) runs a shell or command as them (`identityFor` asks `seamless.EnsureUser`, which waits for the compositor's socket), and stays running. A user who only logs in over ssh gets none until something runs as them through the agent. Verified on a real Ubuntu guest (the hub plus a second user): `caked exec --user bob` starts bob's compositor, `foot` as `admin` and as `bob` show as `[vm] adminterm` and `[vm] bob: bobterm` host windows, killing bob's compositor removes only bob's windows and it comes back; unit tests cover the id translation, routing, title prefix, window cleanup, replacement and a host that goes away. Not exercised: keyboard routing and a third user on a real host, a host speaking protocol 2 through the hub (the guest's compositor was protocol 1), the agent updated in place while compositors run.
- **Needs a cakeagent with `seamless` support** (`CAKEAGENT_VERSION`, a release tag `v1.0.<commit count>` since the rename from `CAKEAGENT_SNAPSHOT`, compared exactly): cakeagent #23 is the first with them, protocol 2 (mouse wheel) came later; an older guest agent ignores the install flags. The pin is **v1.0.334** (the first with the selection exported to an Xwayland that starts after the copy, cakeagent#37) on top of v1.0.332, the first with clipboard items of any MIME type (protocol 4, cakeagent#36), on top of v1.0.329, the first with XWayland (cakeagent#35) on top of v1.0.326, the first with the clipboard (protocol 3, cakeagent#34) on top of v1.0.321, the first built from the compositor sources in the cakeagent repository (cakeagent#33, with the frame buffer and server-side decoration fixes), which also keeps the in-place update fix (cakeagent#32, v1.0.317): updating an agent in place: the guest used to keep its old `caker-seamlessd` forever (`installNeeded` only checked that the file existed), so an agent speaking protocol 2 on a guest whose compositor spoke protocol 1 never got the new one. The agent now compares the installed compositor with the embedded one (sha256) at start and rewrites it (cakeagent#32); the compositors die with the agent (`Pdeathsig`) and come back with the new binary. Verified on a VM updated from an older agent. To try it by hand: build that agent, copy it into the VM and run `cakeagent seamless run --seamless-user <user>`, then `cakeagent seamless launch -- foot`. The agent's own documentation is the cakeagent wiki (`seamless-windows`, `releases`).

Verified on a freshly built VM (`caked build --alias ubuntu2604 --seamless`, agent snapshot `ee64e17b` installed by cloud-init: compositor in `/usr/libexec/caker/`, service flags in the unit, compositor connected on boot, the shell profile installed, and `gnome-terminal`, `nautilus` and `foot` typed as plain commands in an ssh login shell shown as host windows), and earlier with a VM started by a `caked vmrun --ui` built from this branch: Caker created the socket and the server, the guest compositor (run by a dev cakeagent) connected over vsock, `foot` opened as `[seamless-dev] foot`, keystrokes through the real window-focus path reached the guest shell, and stopping the VM removed the socket.

## Windows of a VM that runs under a service, possibly on another host: `SeamlessTunnel`

The VM's socket device connects to a unix socket on the VM's host, so whoever shows the windows has to listen there. A client that is not on that host (`cakectl`, talking to a `caked service` that may be remote) can't, so the stream travels over gRPC like the VNC one does:

```
guest compositor ──vsock──► socket device ──► smls ◄── caked service (SeamlessTunnel) ◄──gRPC──► cakectl seamless ──► SeamlessWindowManager
```

- **RPC**: `SeamlessTunnel(stream SeamlessStream) returns (stream SeamlessStream)`, `SeamlessStream{bytes stream}`, the VM named by the `CAKEAGENT_VMNAME` header (as `VncTunnel`). The bytes are the wire protocol above, untouched: the service never decodes them.
- **Service side** (`Sources/caked/SeamlessTunnel/SeamlessTunnel.swift`): for as long as the client's stream lasts it listens on the VM's `smls` socket (`VMLocation.seamlessSocketURL`) (NIO unix-socket server, `0600`) and pipes the guest connection to the stream and back; a new guest connection replaces the previous one. The compositor retries every second, so it connects once the listener exists and again after a restart; when the client leaves, the listener and the socket go. A listener that fails (NIO gives up on an accepted socket the guest already dropped) is bound again while the client is there. Errors a client can act on are gRPC statuses with a message (`notFound`, `failedPrecondition` when seamless is off, `alreadyExists`).
- **One owner per socket**: `SeamlessServer.acquireListenerLock(for:)` is an `flock` on `<socket>.lock`, taken by `SeamlessServer.start()` and by the tunnel, so Caker.app, a `caked vmrun --ui` and a tunnel can't listen on the same guest. Probing the socket by connecting was tried first and is wrong: the listener takes the probe for the guest and drops the real session. The kernel releases the lock when the process dies.
- **A VM run by the service doesn't listen itself** (`VMRunHandler.launchedFromService`, `VirtualMachine.startSeamlessWindows()`): its windows are shown through the tunnel.
- **Caker.app** (`Sources/caker/Helpers/SeamlessTunnelSession.swift`): for every connection mode but `.app` (a local or a remote service), `VirtualMachineDocument.updateSeamlessTunnel()` keeps one `SeamlessTunnelSession` while a Linux VM with seamless windows is `.running` (called from the `status` and `virtualMachineConfig` observers, so it follows the status events whatever sends them) and stops it otherwise. The session owns the `SeamlessWindowManager` and the `SeamlessTunnelClient`, reconnects every 3 s when the stream ends (service restarted, network blip) and gives up on a permanent refusal (`notFound`, `failedPrecondition`, `alreadyExists`, ...). In `.app` mode the VM runs in the app and `VirtualMachine.startSeamlessWindows()` listens directly. Verified with a real service: Caker.app (not `.app` mode) opens the tunnel when the VM runs, a guest `gnome-terminal` started by `cakectl exec` shows as `Caker [seamless-new] Terminal`, stopping the VM removes the socket and the window, starting it again shows windows again. Not run: a remote service, the reconnect after a service restart (Caker switches back to `.app` mode when the service goes away, which drops the document, so the reconnect only covers shorter outages).
- **Client side** (`Sources/cakedlib/Seamless/SeamlessTunnelClient.swift`, `cakectl seamless <vm>`): the stream becomes one end of a `socketpair`, the other end goes to `SeamlessWindowManager.attach(fd:)` (`SeamlessServer.attach(fd:)`), so the manager works as with a local guest and needs no socket. The command runs an `NSApplication` until Ctrl-C or until the service ends the stream, and prints the service's error otherwise (`terminate` never returns to `run()`, so it is reported before).
- **Verified** with a real service (`caked service listen`) and `cakectl` on the same host: the VM started through the service (`vmrun --service`), `cakectl seamless` shows `gnome-terminal` started by `cakectl exec` as `[seamless-new] Terminal` owned by `cakectl`, a second tunnel is refused with its message while the first keeps running, an unknown or non-seamless VM is reported, Ctrl-C removes the socket. Not run: a service on another host, a client that is slower than the guest (the gRPC callback API has no flow control, so the service-to-client direction buffers in the client's write queue; the frames in flight are capped by `SeamlessServer` once the manager reads).

## `cakectl sh`, `exec` and `seamless`: showing the windows, and who owns them

`cakectl sh`/`exec` on a VM with seamless windows (`config.seamless`, opt out with `--seamless false`) run the shell/command in a background task while the main thread runs an accessory `NSApplication` with a `SeamlessWindowManager` fed by a `SeamlessTunnelClient`; the process ends when either side does (`NSApplication.run()` blocks the main thread, so a task group can't cancel it). Logging to stderr is turned off in that mode, and the app is not activated on launch (it stole focus from the user's window). `cakectl seamless <vm>` is the same without a shell, with a regular app and a Ctrl-C to stop.

Only one process can own a VM's windows (the `flock` above), so a second `sh`/`exec`/`seamless` (another terminal, another `--user`) used to fail with "The windows of VM … are already shown by another process" (`alreadyExists`) and exit. `Sh.SeamlessConnection` (`Sources/cakectl/Commands/Sh.swift`, shared by the three commands) now treats that status as "someone else has them": it releases its manager and tunnel, retries every 2 s while the command keeps running (`cakectl seamless` prints that it is waiting, once), and shows the windows as soon as the owner lets go. Any other error still ends the process with its message. While the owner is up, the second session's guest windows still appear, since every user's compositor goes through the one hub connection; they disappear for about two seconds when the owner exits, until the waiting one takes over. Caker.app's own session (`SeamlessTunnelSession`) is the owner in that case and a waiting `cakectl` stays waiting until it stops. Not run: this against a real VM after the change (it builds, the retry was reasoned, not exercised).

## The guest compositor

`seamlessd/` of the cakeagent repository (`main.c`, `wire.c`, `README.md`, `caker-seamlessd.service`; it was `Tools/SeamlessCompositor/` here until Fred78290/cakeagent#33 moved it next to the agent that embeds and supervises it): a headless wlroots compositor with software (pixman) rendering.

- Each `xdg_toplevel`/`xdg_popup` is announced when it maps. On every commit of the window or any of its subsurfaces it renders the surface tree at `logical * scale` into an offscreen buffer, diffs it against the previous frame to find the changed rectangle, LZ4-compresses it and queues it (non-blocking, 64 MiB cap, then it falls back to a full frame). Updates are coalesced to ~60 fps and frame callbacks are sent after each frame.
- Host input becomes seat events: evdev keys through a virtual xkb keyboard, pointer enter/motion/button/axis hit-tested against the window's surface tree, focus through `xdg_toplevel` activation.
- Scale: the host's output scale is advertised through `wp_fractional_scale` and `preferred_buffer_scale`.
- The host draws the title bar (server-side decorations requested), maximize/fullscreen/minimize requests are acknowledged and ignored.
- It connects to `vsock:5100` (or `unix:`/`tcp:` for testing), retries every second, and re-announces every window when the host reconnects.

It advertises `xdg-activation`, `text-input` and `toplevel-icon` so toolkits stop warning about them: they are accepted and ignored (the host decides focus, there is no input method), and it exits cleanly on SIGTERM (the listeners are removed before the display is destroyed, wlroots asserts otherwise).

Verified in a Caker VM: `weston-simple-shm`, `foot`. Also checked with the agent's fixes (cakeagent#24): `gnome-terminal`, Files (Nautilus) and the snap Firefox (cakeagent#24, #25). Those need the display exported to D-Bus/systemd activation, and Firefox needs a `wayland-N` socket name (snap's AppArmor). Not exercised: popups from a real toolkit, host-initiated resize, fractional scales other than 2x.

## Starting guest applications from the host

The agent already lists the guest's `.desktop` applications and starts them with the compositor's environment (`cakeagent seamless apps --json`, `cakeagent seamless launch --desktop <id>` or `-- <program> …`, `linux/pkg/seamless/desktop.go` in the cakeagent repository). The host runs both through the agent's `Run` call (`/usr/local/bin/cakeagent …`, as root with `--seamless-user=<vm user>`, which the agent resolves to that account's credentials, runtime directory and display), so nothing new is needed in the guest.

- **`CakedLib.GuestApplications`** (`Sources/cakedlib/Seamless/GuestApplications.swift`): the model (`GuestApplication`, the agent's JSON), the command lines, the parsing and the lookup, on top of a `Runner` closure (a command line in, a `Caked_RunReply` out), so a caked service (`client.run`, `Run` RPC), a local `caked` and an embedded VM (`CakeAgentConnection.run`) share it. A desktop file ID and a user name are validated (`isValidIdentifier`/`isValidUser`) before they reach a command line, and a program's words are single-quoted. `resolve(_:in:)` takes a desktop ID (with or without `.desktop`), else a name, else the last word of a reverse-DNS ID (`firefox` for `org.mozilla.firefox`), case-insensitively, and refuses to guess when a step finds several.
- **`cakectl app list <vm>`**, **`cakectl app run <vm> <app>`** (`--command` for a plain program: `cakectl app run <vm> --command -- foot -e htop`), **`cakectl app create-launcher <vm> <app>`** (`Sources/cakectl/Commands/App.swift`), and a local **`caked app list|run|create-launcher`** (`Sources/caked/Commands/App.swift`, no windows: they belong to the process that runs the VM). The VM must be running and a Linux one (`Run` would start a stopped VM, which a listing must not do). `run` needs seamless windows on the VM, starts the application, then owns the windows like `cakectl seamless` does (`Sh.SeamlessConnection`, accessory app) until the VM stops, **unless another process already shows them** (`waitsForOwner: false`: `alreadyExists` ends the process successfully, the application is already started). `--start` starts a stopped VM first and `--wait <seconds>` retries what failed because the agent isn't answering yet (not a wrong name).
- **Launchers** (`CakedLib.GuestApplicationLauncher`): `create-launcher` writes `~/Applications/<name> (<vm>).app` (`--output`, `--force`): an `Info.plist` (`LSUIElement`, identifier `com.aldunelabs.caker.guestapp.<vm>.<desktop id>`) and a `/bin/sh` script `exec`-ing `<tool> app run <vm> <id> --start --wait 120`, every word single-quoted. `cakectl app create-launcher` makes it run `cakectl` (that process shows the windows), `caked app create-launcher` makes it run `caked` itself (`caked app run --start --wait` starts the VM through `vmrun`, which shows the windows of a seamless VM; verified: stopped VM, launcher run, `[vm] foot` window after 6 s) (a test runs the script against a stand-in tool with hostile text). Connection options (`--connect`, `--disable-tls`, `--system`) are kept, **never the password** (it would end in a readable file). Its icon is read from the guest (`GuestApplications.icon(for:run:)`: the `Icon=` name is looked up with `find` in `/usr/share/icons`, `/usr/share/pixmaps`, `/usr/local/share/icons`, `/var/lib/snapd/desktop/icons` and `/var/lib/flatpak/exports/share/icons`; an absolute `Icon=` (snap apps: `/snap/firefox/current/default256.png`) is accepted under those folders, `/snap`, `/var/lib/snapd` and `/var/lib/flatpak`, a PNG of at least 128 points preferred, else the SVG, else the largest PNG; fetched base64 under 2 MB; the name is validated since it comes from the guest), turned into `Contents/Resources/launcher.icns` by `iconutil` (`GuestApplicationLauncher.writeIcon`, SVG drawn by `NSImage`) and set as `CFBundleIconFile`; best effort, a missing or unreadable icon leaves the generic one (verified with foot (SVG), htop (pixmaps PNG); vim, whose `Icon=gvim` is in the guest theme, got one too; the Firefox snap, whose icon is a path under `/snap`). Not code-signed (it runs from a local folder).
- **Caker.app**: an "Applications" button in the VM window toolbar (`HostVirtualMachineView.applicationsButton`, `GuestApplicationsView`) for a running Linux VM with seamless windows and an agent that answers; a popover with a search field, the list (each row shows the application's icon, read from the guest as the row appears by `GuestIconLoader`: one application at a time, two agent calls each, kept for the popover's life; the initial in a tile meanwhile and when there is none), a click starts the application (the windows come through the tunnel or the embedded server the app already has), a "create launcher" button (`plus.app`) shown on the row under the pointer writes the same bundle (`GuestApplicationsHandler.launcherTool`): with the `cakectl` inside the app for a VM of the local service (`.user`/`.system`), and with the `caked` inside the app for a VM the app runs itself (`.app` mode, no service to connect to: `caked app run --start` reaches the agent directly, and the windows stay in the app while it runs the VM). Not for a remote service, whose address the app doesn't pass. The `.app` mode path builds but was not run from the GUI.
- A `Terminal=true` application (htop, vim) runs inside the guest's terminal emulator (`foot -e htop`, found through the `TerminalEmulator` category): started alone by the agent it exited at once. Unit-tested (`GuestApplicationsTests`) and **run against a real Ubuntu guest**: `caked app list`, `cakectl app list`, `app run foot` and `app run htop` (a `[vm] foot` window on the host), `create-launcher` and `open` of the generated `.app`. **Not checked**: the `Run` call's 5 s limit on a guest with many `.desktop` files, a non-default `--seamless-user`, the popover and the toolbar button, a Finder double-click (an unsigned script bundle and Gatekeeper), `--start` waiting for a VM to boot.

## Clipboard (copy and paste)

Any MIME type, both ways (protocol 4; protocol 3 had text only and is still spoken to an older guest). `clipboardItems` (`0x0A` guest to host, `0x8D` host to guest): `u16 count` (1 to 16), then per item `u16 mime length` + MIME type + `u32 length` + bytes; valid distinct MIME types (`type/subtype`, printable ASCII, 3 to 127 bytes, so the X11 pseudo targets are out), no empty item, 32 MiB of data in all (`maxClipboardTotalBytes`, `SEAMLESS_MAX_CLIPBOARD_TOTAL`), checked by the compositor's parser, the hub and the host's codec. Text needs a cakeagent with protocol 3 (cakeagent#34, released in `v1.0.326`); items need protocol 4, for which `CAKEAGENT_VERSION` must be bumped once the cakeagent items PR (cakeagent#36) is released. Xwayland only bridges a selection while one of its surfaces has the keyboard focus.

- **Guest to host**: when an application sets the selection, the compositor reads what it offers at once, one type after another (a pipe each, 3 s for text, 15 s for the rest), and sends `clipboardItems` (protocol 3: only the `text/plain` text, as `clipboard`); `SeamlessWindowManager.setHostClipboard(_:)` maps each item's MIME type to a pasteboard type (`pasteboardType(forMIME:)`: plain text is `.string`, the rest through `UTType(mimeType:)`, kept when it is text, an image or PDF and not a dynamic type; the others are left out), puts them on `NSPasteboard.general` and remembers the change count, so it isn't sent back.
- **Host to guest**: `syncClipboardToGuest()` sends the pasteboard (`clipboardItems(from:)`: the text first, as `text/plain;charset=utf-8`, then every type with a shared MIME type, one item per MIME type, a TIFF as a PNG unless there is one; 16 items and 32 MiB at most; only the text for a protocol 3 guest) when its change count differs from the last one seen, on a window becoming key (`SeamlessWindowController.onFocus`, after the focus message, so the hub already routes it to that user) and every 0.5 s while the application is active with a key window (there is no pasteboard notification). The guest compositor makes it the selection of its seat, offered with its types, and as plain text under the usual names.
- **Not shared**: a pasteboard marked `org.nspasteboard.ConcealedType`/`TransientType`/`AutoGeneratedType` or by 1Password, a type that isn't text, an image or PDF (file references, executables, arbitrary UTIs), what does not fit in 32 MiB, and the clipboard of a user of the guest who doesn't have the focus (the hub drops it, and gives the host's only to the focused user's compositor).
- **Cmd as Control** (`SeamlessSurfaceView`): a Linux application expects Control+C/V/X/A, a Mac user presses Command. Command held with a key is sent as Left Control plus that key, and Command pressed and released alone is the Super key. A Control key already held is left alone.
- The compositor also accepts selection requests (copy and paste between guest applications did not work before either), handles the primary selection (guest only) and offers `wlr-data-control`, so `wl-copy`/`wl-paste` work without a focused surface.
- **Verified**: the compositor against a test host speaking the protocol (`wl-copy`/`wl-paste` both directions, 900 KB host to guest, a 1.1 MB copy dropped), and guest to Mac through the real hub, a running `caked` and `pbpaste` (text with accents). **Checked by the maintainer in a real Caker session**: copy and paste of text works (Cmd+C / Cmd+V between the Mac and a guest window, with the released cakeagent v1.0.326). Not checked one by one: the timer versus the window-becoming-key trigger, other guest applications, a second guest user. Unit-tested: codec limits and formats, version gating, delivery through the server; the hub's routing and validation.

## Keyboard layout (protocol 5)

Keys travel by physical position (evdev codes), so what they type is decided by the guest's XKB layout. Until protocol 5 that was the layout the agent was installed with: `CakeConfig.agentServiceFlags` writes `--seamless-layout=<layout of the Mac that generated the flags>`, so a French user on a remote Mac (`cakectl seamless`, Caker.app on another host) typing into a guest installed from a US Mac got US characters (the key labelled Q sits where a US keyboard has A, and the guest answered `a`).

`keyboardLayout` (`0x8E`, host to guest): one string, an XKB layout name (`SeamlessProtocol.isValidKeyboardLayout`: lowercase letters, digits and underscores, starting with a letter, 32 bytes at most, or empty), checked by the host's codec, the hub and the compositor's parser. It is sent by the process that shows the windows (`SeamlessWindowManager.syncKeyboardLayoutToGuest()`, so the Mac of the viewer, whichever Mac runs the VM) when the guest connects, whenever a window becomes key and on the 0.5 s timer while the application is active (the layout is `SeamlessKeyboardLayout.hostXkbLayout()`), and only when it differs from what the guest was last told. A layout with no plain XKB equivalent (Dvorak...) is sent as empty, which puts the compositor back on the layout it was installed with (`--seamless-layout`), and nothing is sent at all when this Mac has none and the guest was never told one. The compositor compiles a new keymap at once; the hub gives it to every compositor and to one that attaches later. `--seamless-layout` stays the starting layout, and what a host on protocol 4 gets. Needs a cakeagent with protocol 5: `CAKEAGENT_VERSION` must be bumped once it is released.

## X11 applications (XWayland)

An application that only speaks X11 (GIMP 2.10 is GTK2) failed with "Cannot open display": the guest compositor had no X server. It now serves an X display through wlroots' XWayland support (cakeagent#35, released in `v1.0.329`, protocol unchanged): wlroots listens on a free display at start and runs `Xwayland` when the first X11 client connects, X11 windows are announced like xdg ones (managed windows are toplevels at the X origin, override-redirect menus and tooltips are popups of a window of the same process), and the compositor writes its display name to `$XDG_RUNTIME_DIR/<socket>.display`, from which the agent exports `DISPLAY` and the `wayland,x11` toolkit fallbacks. The guest needs the `Xwayland` program: `ssh-install-cakeagent.sh` and `cloudinit-install-cakeagent.sh` install it best effort when `--seamless` is among the service flags (apt, dnf, yum, zypper, apk, pacman). **Checked on a real Ubuntu arm64 guest**: `xclock` and GIMP 2.10.36 show as `[vm] …` windows. Not done: the cursor an X11 client draws, Retina sharpness (X11 clients ignore the scale), the pin is `CAKEAGENT_VERSION` = `v1.0.332`.

## Not done yet / known gaps

- Clipboard files, lazy fetching of big types (everything offered is read at once, within the limits), drag and drop (message ids are free, nothing is reserved), client-drawn cursor images.
- Input methods / IME and character-level text input: `text-input` is advertised and ignored, keys go by physical position, and the guest keyboard layout is the one the viewer's Mac sends (protocol 5; a layout with no plain XKB equivalent stays on the installed one). Cmd shortcuts handled by the host menu (Cmd+Q, Cmd+W, Cmd+H...) are not forwarded; the others are, as Control (see Clipboard).
- Launching with arguments or files (`%U`, `%F`) is not supported: `cakeagent seamless launch --desktop` starts the application bare. Not done: a launcher for a VM of a remote service, grouping by `Categories`.
- Host-driven output scale changes when a window moves between displays (`output` exists, nothing sends it on a screen change).
- Rendering: each frame snapshots the whole buffer into a `CGImage`. Replace with an `IOSurface` ring and per-damage updates, and coalesce to the display refresh.
- Compression: LZ4 only. Large animated windows may want a video codec (VideoToolbox decode, software encode in the guest).
- No accelerated 3D: Virtualization.framework gives Linux guests no GPU. A custom virtio device is the only path there, and a big project.
- A burst of guest output faster than a gRPC client reads is buffered in the client's write queue (no flow control in the callback API); a service on another host is not run; Alpine/OpenRC and mounts changes of the agent update path were not booted; a third guest user and keyboard routing through the hub were not exercised on a real host.
- Not run in the sandboxed App Store build (a socket device is created the same way, unverified).
