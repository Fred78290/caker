# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What is Caker?

Caker is a macOS-only toolchain for building and managing virtual machines using Apple's Virtualization framework (requires macOS 15+). It consists of four main executables and a shared library, all defined as Swift Package Manager targets in `Package.swift`.

## Build Commands

```bash
# Basic Swift package build (CLI tools only)
swift build -Xswiftc -D -Xswiftc SPARKLE

# Run all Swift package tests
swift test

# Run a single test class
swift test --filter CakerTests.<TestClassName>

# Signed debug build (requires certificates)
./Scripts/build-signed-debug.sh

# Signed release build
./Scripts/build-signed-release.sh
```

**Web UI** (`webui/`, requires Node.js ≥ 18):
```bash
cd webui && npm install
npm run dev          # Vite dev server on :5173 proxying /1.0 to caked

```

**Integration tests** (`integration/tests/`, Python pytest):
```bash
pip install -r integration/tests/requirements.txt
pytest integration/tests/
```

## Architecture

### Component Map

| Target | Source | Role |
|---|---|---|
| `caked` | `Sources/caked/` | Core daemon: gRPC server, optional LXD REST API, launchd service |
| `cakectl` | `Sources/cakectl/` | CLI client — talks to caked over gRPC |
| `caker` (Caker.app) | `Sources/caker/` | macOS SwiftUI desktop app, embedded VM runner |
| `CakedLib` | `Sources/cakedlib/` | Shared core: VM logic, networking, OCI, Cloud-Init, importers |
| `GRPCLib` | `Sources/Grpc/` | gRPC contract + generated client/server code |
| `VirtualInstallSPI` | `Sources/VirtualInstallSPI/` | C shim exposing private `MobileDevice`/`Virtualization` SPIs, used by `CakedLib` |

### Communication Flow

```
cakectl ──gRPC──► caked (gRPC server)
                     │
LXD/lxc ──REST──►   │  (--rest flag: Vapor HTTP/HTTPS on :8080/:8443)
                     │
webui ──REST──►      │  (served at /ui by caked's Vapor server)
                     │
Caker.app ──gRPC──►  │  (also uses GrandCentralDispatcher stream for live status)
                     │
                  VMRunService ──► VMs (gRPC or XPC per-VM backend)
```

When `caked` is running as a service, operations should go through `cakectl` rather than direct `caked` command invocation.

### Key Subsystems in CakedLib

- **`VMRunService/`** — Two backends for per-VM process management: `GRPC/` (network-based) and `XPC/` (inter-process). Each running VM spawns its own service.
- **`OCI/`** — OCI container image management (pull, push, purge, store).
- **`CloudImage/`** — Cloud image support: `CloudInit.swift`, `SimpleStreams.swift` (Ubuntu streams), `ImageCache.swift`.
- **`Importers/`** — Import VMs from Multipass or VMware.
- **`VNCLib/`** — VNC tunnel support (via RoyalVNCKit).
- **`VMNet/`** — Virtual network management (bridged, hosted, NAT modes).
- **`CakerEnv.swift`** — `.cakerenv` YAML format describing multi-VM environments with dependency ordering.
- **`Config.swift`** — `CakeConfig` backed by `config.json` and `cake.json` files per VM.
- **`PackerLite/`** — drives a freshly-installed VM's unattended first-boot setup (macOS Setup Assistant from an IPSW, or a Linux first-boot installer from an ISO): `PackerLiteDriver.swift` replays a parsed `boot_command` via its own in-process `CGEvent`/`NSEvent` synthesis and Vision OCR, `PackerLiteEngine.swift` owns the boot/provision/shutdown lifecycle, `PackerLiteTemplateResolver.swift` picks a template, and `PackerLiteTemplate.swift`/`BootCommand.swift`/`MacOSVersion.swift` hold the parsing/model types — all part of `CakedLib` itself (no separate SPM target). See [Architecture: PackerLite](#packerlite-unattended-os-provisioning) below.

### gRPC Contract

The single source of truth is `Sources/Grpc/service.proto`. The generated files `service.grpc.swift` and `service.pb.swift` **must not be edited manually** — regenerate them with:

```bash
cd Sources/Grpc && ./generate.sh
```

This script clones `grpc-swift`, builds the protoc plugins, then runs `protoc`. The `VMRunService` has its own separate proto at `Sources/cakedlib/VMRunService/GRPC/mount.proto`.

### LXD REST API

Enabled with `caked service listen --rest`. The Vapor-based server is in `Sources/caked/REST/`:
- `LXDRESTServer.swift` + `Routes.swift` — server setup and route registration
- `Controllers/` — one controller per LXD endpoint group (instances, networks, images, etc.)
- `LXDModels.swift` — Codable types mirroring the LXD REST API
- `LXDOperationStore.swift` — async operation tracking

The TypeScript counterpart lives in `webui/src/types/lxd.ts`.

### GrandCentral Pattern

Caker.app subscribes to the `GrandCentralDispatcher` gRPC streaming call to receive live VM status (CPU, memory, screenshots, state changes). Each running VM calls `GrandCentralUpdate` to push its status to `caked`, which then fans out to connected GUI clients. This is how the desktop app stays in sync without polling.

### SwiftUI front-app activation from a terminal launch

`caked`'s GUI paths (`MainApp.swift`, used by `caker` and by `caked provision --foreground`) are sometimes launched via fork/exec from a terminal or shell script rather than through Finder/LaunchServices. macOS does not automatically grant a process launched that way frontmost/active status, and SwiftUI's `App`/`WindowGroup` scene lifecycle alone doesn't compensate — the window can open fully behind other apps with no visible cue that it exists. `AppDelegate` works around this with a plain `NSWindow` splash screen (not a SwiftUI `Window`/`WindowGroup` scene) shown at `.floating` level via `NSHostingView`, plus three layered activation attempts (`NSApp.activate(ignoringOtherApps:)` in `Extensions.swift`'s `setDockIcon()`, the splash window's own `.floating` level, and a 2s-delayed `NSApp.activate()` fallback — originally 5s, tightened once the pattern proved reliable), transitioning to the real `WindowGroup` via `EnvironmentValues().openWindow(id:)` once `applicationDidBecomeActive` actually fires. **`SplashScreenView` and its `showSplashWindow(name:)` factory now live in `Sources/cakedlib/UI/SplashScreenView.swift`** (moved out of `caked`'s own `MainApp.swift`), specifically so `Sources/cakedlib/UI/VNC/VNCApp.swift` — the standalone VNC client window `cakectl provision` launches inline (see PackerLite section below) — can reuse the exact same splash-then-activate workaround via its own `AppDelegate.applicationWillFinishLaunching`, rather than duplicating it. See the "Front-app activation workaround" comment block above `caked`'s `AppDelegate` in `Sources/caked/MainApp.swift` for the full explanation of why each layer exists — `VNCApp`'s copy is intentionally lighter (calls `SplashScreenView.showSplashWindow` directly) since the underlying rationale is identical.

### PackerLite (unattended OS provisioning)

PackerLite drives a VM's unattended first-boot setup after `VMBuilder.swift` finishes installing it — macOS Setup Assistant for `.ipsw` builds, or a Linux first-boot/OEM installer for `.iso` builds — via a parsed `boot_command`, the same concept as HashiCorp Packer's `boot_command` / `packer-plugin-tart`, built natively with no external binary or plugin. It only runs when `--autoinstall` is passed to `build`/`create`; there's no automatic provisioning otherwise. The two source types resolve their template very differently:

- **IPSW (macOS)**: `PackerLiteTemplateResolver.resolve(...)` (`Sources/cakedlib/PackerLite/PackerLiteTemplateResolver.swift`) picks the template in this order, throwing if none apply: explicit `--template <path>` → macOS version auto-detected from the IPSW filename (`MacOSVersion.detect(fromIPSWFilename:)`, Apple's `UniversalMac_<version>_<build>_Restore.ipsw` convention, which also yields the dotted version string, e.g. "15.6") → explicit `--macos-version` → failure. Built-in templates are bundled as `CakedLib` SPM resources at `Sources/cakedlib/PackerLite/Resources/vanilla-*.packerlite.yaml`, one per version: `macos12`, `macos13`, `macos14`, `macos15`, `macos26`, `macos27` — all six now ship a template, including `macos27` (added alongside the rename below; it was the last gap). **`MacOSVersion`'s raw values were renamed from marketing names to numeric identifiers** (`monterey`→`macos12`, `ventura`→`macos13`, `sonoma`→`macos14`, `sequoia`→`macos15`, `tahoe`→`macos26`, `goldengate`→`macos27`) — the enum itself, `bundledTemplateResourceName`, the bundled `.packerlite.yaml` filenames, and the proto's `Caked_MacOSVersion` cases all moved together. Old marketing names still work as `--macos-version` input: `GRPCLib.MacOSVersion.init?(argument:)` (`Sources/Grpc/options/BuildOptions.swift`) checks a `formerNames: [String: MacOSVersion]` lookup before falling back to `init(rawValue:)`, so existing scripts/docs using `tahoe` etc. keep working — but `MacOSVersion.allCases`/`.rawValue` (used for `--help` text, `CakeConfig.osName` storage, and template filenames) only ever produce the numeric form now. The detected codename/version are persisted unconditionally into `CakeConfig.osName`/`osRelease` (regardless of `--autoinstall`), so a later standalone `caked provision` run knows what the VM is without the original IPSW.
- **ISO (Linux)**: `PackerLiteTemplateResolver.resolveLinuxTemplate(...)` mirrors the macOS resolver but keyed on distro instead of version: explicit `--template <path>` → distro auto-detected from the ISO filename/URL via `GRPCLib.SupportedPlatform(rawValue:)` → bundled default for that platform, if one exists (`Sources/cakedlib/PackerLite/Resources/linux-{fedora,fedora-server,centos,redhat,opensuse,debian,alpine,ubuntu,ubuntu-server}.packerlite.yaml` — nine templates now) → otherwise `nil` (not an error) — the expected outcome for a distro caker doesn't recognize, or for Ubuntu Desktop if a future case ever wants that (see below, it currently does have one). `VMBuilder` only runs PackerLite for an ISO build when `--autoinstall` is set and this resolves to non-nil content. Unlike their original "reviewed for plausibility only" state, CentOS, Fedora (both variants), Debian, and openSUSE have all since been substantially rewritten to use OCR-based `<locate>` navigation instead of fixed clicks/delays, through several rounds of fixes explicitly aimed at matching what the real installer actually shows — evidence of iteration against real boots, even though no commit claims full end-to-end validation. Alpine and both Ubuntu templates are the newest additions and are explicitly reviewed-but-not-validated-end-to-end, same caveat the rest historically carried. `caker`'s VM creation wizard (`Sources/caker/Views/VirtualMachineWizard.swift`) surfaces an optional YAML file picker for ISO sources — required only when `PackerLiteTemplateResolver.hasBuiltInLinuxTemplate(for:)` is false for the detected platform.
  - **Ubuntu now has built-in templates too** (`linux-ubuntu-server.packerlite` for Server, `linux-ubuntu.packerlite` for Desktop — `SupportedPlatform.bundledPackerLiteTemplateResourceName(desktop:)` branches on `desktop` for `.ubuntu` the same way it already did for `.fedora`) — this is genuinely new: Ubuntu previously had no PackerLite path at all, since its ISO already ships its own native cloud-init/subiquity "autoinstall" unattended-install mechanism. These bundled templates are an *alternative* route to the same outcome via PackerLite's usual OCR-driven `boot_command` approach, not a replacement for Ubuntu's own autoinstall — and notably their `boot_command` content doesn't type the account credentials at all (unlike every other bundled Linux template): it only navigates the GRUB boot menu and keyboard layout, then waits for subiquity's own autoinstall flow to run to completion unattended on its own. **Bug found and fixed while syncing this doc**: both files existed and the resolver's server-case wiring already returned `"linux-ubuntu-server.packerlite"`, but neither was registered in `Package.swift`'s `.copy(...)` resource list — so `Bundle.module` could never actually find them, and resolving Ubuntu threw `"No built-in provisioning template is bundled for ubuntu yet"` at runtime despite the resolver code claiming otherwise; the desktop case was also still hardcoded to `nil` even though the Desktop template file already existed, unused. Exact same class of bug as the Alpine gap documented below — fixed both, and closed a real, currently-broken test in the same pass (`testUbuntuHasNoBuiltInLinuxTemplateAndResolvesToNil` was asserting the old, now-false, behavior — replaced with `testUbuntuHasBuiltInServerAndDesktopTemplates`). Also found and fixed while investigating this: `linux-alpine.packerlite.yaml`, `linux-ubuntu-server.packerlite.yaml`, and `linux-ubuntu.packerlite.yaml` all had a wrong header comment block — literally the Alpine setup-alpine header verbatim, including the "# vanilla-alpine324.packerlite.yaml" filename comment on line 1 — copy-pasted and never updated for the latter two; corrected all three.
  - **A second, unrelated set of pre-existing test failures surfaced by the same pass**: `assertLinuxTemplateLoadsAndParses` (the shared "does this file load AND fully parse" test helper, distinct from and stricter than the resolver's own "does the raw content load" tests) only ever supplied `["username", "password"]` as substitution variables — three Linux templates had since started referencing `${var.hostname}`/`${var.ssh_authorized_key}` (see `setupVariables()` below) and RedHat's now declares `required_variables` for two vars the fixture never supplied (see below) — none of which had been caught because nobody had run this specific test file fresh since those commits landed. Fixed the fixture to supply all of them; added the missing `testLinux{Alpine,UbuntuServer,UbuntuDesktop}PackerLiteTemplateFileLoadsAndParses` coverage while in the file, since none of the three had any parse-level test at all before this.

This is the identical class of bug the macOS-version-rename `Package.swift` gap and the missing `<scroll>` dispatch line above already documented: a new resource/case added in one place without updating every other place that has to agree, compiling cleanly and failing silently (an Alpine ISO build with `--autoinstall` and no `--template` would just skip provisioning with no error, same as an unrecognized distro). **`SupportedPlatform(rawValue:)` bug fixed alongside this**: the substring match used to compare a lowercased input against un-lowercased case raw values, so `.openSUSE` (raw value `"openSUSE"`, mixed case) could never match — including reading back a value the type itself had written via `CakeConfig.configuredPlatform`'s setter. Also added `"rhel"` as an alias for `.redhat`, since official RHEL ISO filenames use that, not `"redhat"`. See `Sources/grpc/VirtualMachineConfiguration.swift`.

In both cases the VM's account always comes from `CakeConfig.configuredUser`/`configuredPassword` (`--user`/`--password`), injected into the template as `${var.username}`/`${var.password}` — templates must not declare their own.

**`PackerLiteEngine`** (`Sources/cakedlib/PackerLite/PackerLiteEngine.swift`) now has three entry points, plus a private step-runner shared by all of them:
- A public `provision(vm:targetView:commands:resolvedBootTimeout:progressHandler:)` just replays one already-parsed `BootCommandSteps` sequence against a target `NSView` under a `resolvedBootTimeout` watchdog — no template/IP/agent logic, purely "run these steps." (`ProvisionHandler` also calls this directly for the `pre_boot_command` phase — see below — so it can no longer be `private`.)
- `provision(vm:template:runningIP:runMode:progressHandler:)` drives an already-running `VirtualMachine`'s **`boot_command`** phase (`template.bootCommand`, already parsed — see `ParsedPackerLiteTemplate` below — handed straight to the step-runner above), then — once an IP is available — installs the cakeagent and sets `config.agent = true`. Used by `CakedLib.ProvisionHandler` (`Sources/cakedlib/Handlers/ProvisionHandler.swift`), the shared standalone-provisioning entry point both `caked provision` and the `Provision` gRPC RPC delegate to, which boots the VM itself (with a UI window locally, headlessly-but-with-VNC over gRPC) instead of assuming a caller already booted it.
- `provision(id:location:config:template:runMode:progressHandler:)` is the build-time orchestrator — called from `Sources/cakedlib/Handlers/BuildHandler.swift` as an explicit **post-build** step (after the VM is relocated from its temp directory to its permanent location), not inline inside `VMBuilder.swift` anymore (`VMBuilder` no longer contains any provisioning logic at all). It owns the **full two-stage pipeline**: it starts the VM itself (`vm.startVM()`), runs an optional **`pre_boot_command`** phase immediately — before any IP is available — then waits for an IP via `location.waitIPWithLease(config:wait:runMode:)` and hands off to the `runningIP`-based overload above for the main `boot_command` phase + agent install. `id: UUID` is the build session's identifier (see "Stable build-session UUID" below) — this overload also tracks the in-flight `VirtualMachine` in `PackerLiteEngine.provisioned: [UUID: VirtualMachine]` and posts `provisionedStartNotification`/`provisionedTerminatedNotification` (keyed by that UUID in `userInfo["wizardID"]`) when running inside `caker` (`Bundle.runInCaker`), so the VM creation wizard can show the live VM view inline during provisioning instead of only in a separate debug window (see `Sources/caker/Views/VirtualMachineWizard.swift`, `PackerLiteEngine.provisionedStartNotification`/`.provisionedTerminatedNotification` handlers).

**`ParsedPackerLiteTemplate` now separates parsing from the raw template model.** `PackerLiteTemplate` (`Sources/cakedlib/PackerLite/PackerLiteTemplate.swift`) is a `Codable` decode-only DTO whose fields (`variables`, `bootTimeout`, `preBootCommand: [Command]?`, `bootCommand: [Command]?`) are all `private` now — nothing outside the file touches them directly. `@MainActor public static func load(from:variables:) throws -> ParsedPackerLiteTemplate` (and a `fromFile:` overload, `async`, since it also does file I/O) decodes the YAML, substitutes `${var.*}`, and fully parses `boot_command`/`pre_boot_command` in one call, returning `ParsedPackerLiteTemplate` — a small `Sendable` struct with `bootTimeout: TimeInterval` (already resolved, not a string) and `preBootCommand`/`bootCommand: BootCommandSteps` (already-parsed `[BootCommandStep]`, not raw `[Command]`). Callers (`PackerLiteEngine`, `ProvisionHandler`) work with this parsed value directly — there's no more separate `parsedBootCommand()`/`resolvedBootTimeout` step to call. **This also removed `async` from the whole boot-command parsing path** (`BootCommand.parse`, `BootCommandStep.init`) — the earlier `TISInputSource`-driven keyboard-layout lookups that required it are now wrapped in the `@MainActor`-isolated `load`/`parse` instead, so `PackerLiteTemplate.load` can be called synchronously (well, via one `@MainActor` hop) from inside `VMRunHandler`'s run closure rather than needing a detached `Task`.

`pre_boot_command:` (`PackerLiteTemplate.preBootCommand`, parsed the same way as `bootCommand`) exists specifically for Linux ISO installs: some distros' GRUB boot menus need early keystrokes (navigate + Enter) sent before the installer has come up far enough to have an IP — previously this was covered by a blind wait before the main `boot_command` phase even started; several bundled Linux templates (`linux-{centos,debian,fedora,opensuse,redhat}.packerlite.yaml`) now use `pre_boot_command` for that GRUB-navigation step instead, cutting the blind wait from ~30s down to 5s. macOS templates have no use for `pre_boot_command` — Setup Assistant only ever starts after the OS is already up.

Both `PackerLiteEngine.provision` entry points that reach the runningIP-based overload mark `CakeConfig.provisioned = true` on success via the shared driving path.

**Standalone provisioning is now available three ways**, all converging on `CakedLib.ProvisionHandler.provision(...)`:
- `caked provision <vm>` (`Sources/caked/Commands/Provision.swift`) — local-only, boots the VM with a visible window via `VMRunHandler` so the operator on that host can watch.
- `cakectl provision <vm>` (`Sources/cakectl/Commands/Provision.swift`) — the gRPC client, added alongside a new server-streaming `Provision` RPC (`Sources/Grpc/service.proto`: `ProvisionRequest`/`ProvisionStreamReply`/`ProvisionedReply`, mirroring `Build`'s streaming pattern) so provisioning can be driven remotely, same as `build`/`launch`. **Must be registered in `Client.swift`'s `subcommands:` array** (`Sources/cakectl/Client.swift`) like every other cakectl command — this was initially missed when the command file was added, leaving `cakectl provision` invisible to ArgumentParser despite the file, the proto RPC, and the server handler all being wired up; worth double-checking after adding *any* new cakectl command, since a missing registration compiles cleanly and fails silently (the command just doesn't appear in `--help` or parse).
- The `Provision` RPC's server-side handler is `Sources/caked/Handlers/ProvisionHandler.swift` (`ProvisionHandler: CakedCommandAsync`, dispatched from `CakedProvider.provision(request:responseStream:context:)`), which streams `.progress`/`.step`/`.substep`/`.terminated` back to the client exactly like the `Build` RPC does, ending in a `ProvisionedReply`.

**`cakectl provision` now opens a live VNC window inline**, instead of just printing progress until completion. `CakedLib.ProvisionHandler` starts the VM's VNC server as soon as it's up and sends a new `.infos(ProvisionInfo)` progress event (`ProvisionInfo`: VNC URL, screen size, `CakeConfig`) over the stream — `ProvisionStreamReply.ProvisionInfo` (field 6 in `Sources/Grpc/service.proto`). `cakectl`'s `Provision` command (`Sources/cakectl/Commands/Provision.swift`) changed from `AsyncGrpcParsableCommand` to `GrpcParsableCommand` specifically to support this: its synchronous `run(client:arguments:callOptions:)` wraps the whole async streaming loop in `withCheckedThrowingContinuation`, resuming as soon as an `.infos` event arrives (via a `Synchronization.Mutex`-guarded `resume(_:)` helper, since both the stream-reader task and a clean-completion path can race to resume it) rather than waiting for the stream to fully finish. Once resumed with `ProvisionInfo`, it opens an SSH-tunneled VNC session through `VNCApp.startVncClient(...)` (`Sources/cakedlib/UI/VNC/VNCApp.swift`) — the same `VNCApp` used elsewhere for post-build VNC viewing — reusing the shared `SplashScreenView` splash-then-activate workaround described above while it connects. Progress/step/substep events continue streaming and printing in the background for the remainder of the run.

Template `boot_command` entries are `{title, command}` objects (not bare strings) — the `title` surfaces as a progress substep and in logs. `BootCommand.swift`'s token vocabulary covers waits, text/press/click, `<leftShiftOn>`/`<leftShiftOff>`-style modifier holds (including `<fnOn>`/`<fnOff>`), `F1`–`F20`, `<click 'On-screen text'>` (Vision OCR), and `<keyboard 'source-id'>` to switch the active TIS keyboard-layout translator at runtime (`'current'` captures whatever layout is active on the host). `PackerLiteDriver` synthesizes `CGEvent`/`NSEvent`s directly against the VM's rendered `NSView` — it no longer wraps `VNCInputHandler`, just reuses the same synthesis technique in-process. `parseAttributes(_:token:)` (shared by the `click`/`locate`/`skipCommandIfNotFound`/`scroll` attribute-style tokens) now takes an explicit `token` name and throws a dedicated `.malformedAttribute` case instead of always throwing `.malformedClick` regardless of which token actually failed to parse — a leftover from `click` being the first attribute-style token added, before the others copied its parsing without generalizing the error too. A separate misclassified `.malformedClick` throw in the keyboard-parsing path was also corrected to `.malformedKeyboard`.

**`<clickText>`/`<locate>`/`<skipCommandIfNotFound>` now accept a pipe-delimited list of OCR alternatives** — `text="Accept|Continue"` matches if *any* of the strings is recognized on screen, not just one exact string. `.clickText`/`.locate`/`.skipCommandIfNotFound`'s associated value changed from a single `String` to `[String]` accordingly (`trimMatchingQuotes(textValue).split(separator: "|").map { String($0) }` at every parse site, including the legacy unquoted-string form). Useful for text that's worded differently across installer versions/locales without needing a separate `<locate>` step per wording.

**New token: `<skipStepIfNotFound text=... steps=N timeout=N>`** (default `steps: 1`, `timeout: 10`) — like `<skipCommandIfNotFound>`, but instead of breaking out of the *rest of the current title block* when the text isn't found within `timeout`, it skips exactly the next `N` steps and then continues normally with whatever comes after them. `<skipCommandIfNotFound>`'s all-or-nothing "abandon the rest of this title" granularity was sometimes too coarse for an installer screen where only a couple of steps are conditional, not the whole block. (`<skipCommandIfNotFound>`'s previous, shorter name was renamed to this one for clearer contrast with `<skipStepIfNotFound>` — "skip the rest of this **command**'s steps" vs "skip **N steps**" — a pure naming change with no behavior change; while touching this, `parseSkipStepIfNotFound`'s error paths were also found to be throwing `.malformedSkipCommandIfNotFound` (that other token's own error case) instead of one of its own, a leftover from copy-pasting — given a dedicated `malformedSkipStepIfNotFound` case instead.)

**Debug overlays are no longer `#if DEBUG`-only** — the OCR text-box and click-target highlight overlays (used by `caked record`'s locate-mode toggle, and internally by `PackerLiteDriver` when driving a template) now gate on runtime trace-level logging instead of a compile-time flag, so they can be turned on/off in a release build via log level rather than requiring a debug rebuild. Split into separate text-box and click-target overlay layers, and a new `showTextesBox` helper (sic — existing name, not fixed here) draws every OCR observation on screen when trace logging is active, useful for diagnosing why a `<locate>`/`<click text=...>` step isn't finding what it expects.

**`ignore_ip: true` template field**: when set, both the build-time orchestrator (`PackerLiteEngine.provision(id:...)`) and the standalone-provisioning path (`CakedLib.ProvisionHandler`'s `ProvisionTask`) skip waiting for the VM's IP address before/after the main `boot_command` phase entirely, instead of throwing if one never becomes available. For a template whose `boot_command` never actually needs network access (or a guest where DHCP is unreliable/slow enough that waiting for it is more likely to fail the whole run than just skip it) — several of the Linux templates now set this (e.g. Debian's, alongside its "complete login after installation" rework). Note this is a template-level opt-out from IP-waiting, not from agent installation specifically — a template with `ignore_ip: true` also won't get the post-provisioning cakeagent install step, since that itself depends on having an IP.

**`post_boot_command: [String]` template field** — a list of shell commands run sequentially, over their own SSH connection (`VMLocation.executePostBootCommand(_:config:runningIP:timeout:runMode:)`, following the exact same `createSSH`/three-way-`authenticate` pattern `installAgent` already uses, not the cakeagent's own exec RPC), right after the `install_agent` step (whether or not it actually ran — `PackerLiteEngine.provision(vm:template:runningIP:...)` gates `post_boot_command` only on `runningIP` being available, deliberately not on `template.installAgent`, so a template with `install_agent: false` can still use it). Stops on the first command that exits non-zero rather than continuing past a failure. Like `boot_command`/`pre_boot_command`, entries support `${var.*}` substitution (`PackerLiteTemplate.resolvingVariables(_:)` now substitutes into `postBootCommand` too, not just the two `Command`-based fields) — so a `post_boot_command` entry can reference `${var.username}`, `${var.hostname}`, `${var.ssh_authorized_key}`, or any custom `--var`-supplied name.

**`waitIPTimeout` (default 180s) is now a parameter on `PackerLiteEngine.provision(vm:template:runningIP:runMode:waitIPTimeout:progressHandler:)`** instead of a hardcoded `180` inside the function — matches the same `waitIPTimeout` convention already used throughout `start`/`launch`/`restart`/`up`/`exec`/`sh`. Not yet exposed as a `--wait-ip-timeout`-style flag on `provision`/`build --autoinstall` specifically (nothing currently overrides the default), but the plumbing is there if a caller needs to. A `.step("Wait IP address…")` progress event and a resolved-IP-or-failure log line were added around the wait, for visibility into what was previously a silent blocking call.

**`required_variables: [String]` template field** — a template can declare variable names it depends on; `PackerLiteTemplate.load(...)` throws `PackerLiteTemplateError.requiredVariableNotFound(variable:)` at resolve time if any of them is missing from the merged variable set, instead of silently substituting an empty string (or leaving `${var.x}` unsubstituted, which would only surface later as a confusing parse/behavior error deep in a `boot_command` run). `linux-redhat.packerlite.yaml` is the first user: it declares `required_variables: [redhat_username, redhat_password]` for the Red Hat subscription-manager registration credentials it now needs (see `a31c148e` below) — these are deliberately separate from the VM's own `${var.username}`/`${var.password}`, since a Red Hat account is a different credential from the VM's local admin account, and there's no sane default to fall back to if it's missing (unlike `ignore_ip`/`install_agent`, which have sensible defaults).

**Conditional title blocks: `<set name="value">` + `condition:`** — a `boot_command`/`pre_boot_command` title block can declare `condition: [expr, ...]` (note the YAML key is singular even though it's a list — `PackerLiteTemplate.Command.CodingKeys` maps `conditions = "condition"`); every listed expression must hold (AND, not OR) for the block to run at all, otherwise `PackerLiteEngine`'s step-runner logs `"Discard command: ..., missing condition"` and skips straight to the next title block without executing any of its steps. Each expression is `name != "value"` or `name == "value"` (quotes optional, `BootCommandStep.evaluateCondition(_:variables:)`) — a variable that was never set compares as an empty string, not as absent, so `version != "44"` doubles as "the earlier `<set version=...>` step on some other title block never actually ran." `<set name="value">` (`BootCommandStep.Step.set`) is the only way to populate one of these runtime variables — parsed via the same `parseAttributes` helper every other attribute-style token uses, except here the attribute *name itself* is the (arbitrary) variable being set, not a fixed attribute like `text=`/`timeout=`. This is a genuinely separate variable namespace from `${var.*}` template substitution: `${var.*}` is resolved once, at template-load time, and baked into steps' literal text before the driver ever runs; `<set>`/`condition:` variables live in `PackerLiteDriver.variables`, mutate as a `boot_command` run actually executes, and reset per driver instance — so state set by a `pre_boot_command` phase's own (separate) driver does **not** carry over into the main `boot_command` phase's driver, only within a single phase's own title-block sequence. `PackerLiteEngine.provision(targetVirtualMachine:commands:resolvedBootTimeout:variables:progressHandler:)` (the shared step-runner) seeds a fresh driver's starting variable set from `ParsedPackerLiteTemplate.variables` (the fully-resolved `${var.*}` dict, reused here as the seed rather than duplicating a second merge) — every one of its three call sites (`PackerLiteEngine.swift`'s own `boot_command`/`pre_boot_command` phases, plus `ProvisionHandler.swift`'s standalone-provisioning `pre_boot_command` phase) passes `template.variables` through. `fedora.packerlite.yaml` is the first real user: a "Wait Fedora 44 setup" title block conditionally skips itself via `<skipCommandIfNotFound text="Welcome to Fedora Linux">` and, if it didn't skip, sets `<set version="44">`; a later "Wait Fedora 43 setup" fallback block is gated on `condition: [version != "44"]`, so it only runs when the Fedora-44-shaped welcome screen was never found.

**`install_agent: Bool` template field** (default `true`) — when `false`, `PackerLiteEngine.provision(vm:template:runningIP:...)` skips the "Install agent…" step entirely, even once an IP is available. For a template provisioning a guest where the cakeagent isn't desired or applicable — `linux-alpine.packerlite.yaml` is the first to set this to `false`.

**`hostname`/`ssh_authorized_key` are now always-available template variables**, alongside `${var.username}`/`${var.password}`. `BuildHandler.build(...)`'s previously-duplicated (one copy for the IPSW path, one for the Linux/ISO path) variable-injection logic was extracted into a shared local `setupVariables()` closure that builds the full merged dict once: starts from `options.provisionVarsDict` (user-supplied `--var`/stored `ProvisionVariablesStore` entries, see below), then unconditionally overwrites `username`/`password` (from `configuredUser`/`configuredPassword`, as before — a template still can't override the account), adds `hostname` (from `options.name`, the VM's own name), and adds `ssh_authorized_key` (the configured SSH public key(s), newline-joined, via `CloudInit.sshAuthorizedKeys(...)` — `nil`/omitted if none configured, rather than an empty string). `8e77785f` migrated several Linux templates from typing a hardcoded `${var.username}-vm` as the hostname to using the real `${var.hostname}` value, and added SSH key setup (writing `${var.ssh_authorized_key}` into `~/.ssh/authorized_keys` post-install) across them.

**Provisioning variables now persist to `<CAKE_HOME>/ProvisionVariables.json`, and are available from every entry point, not just the GUI wizard.** `ProvisionVariable`/`ProvisionVariables`/`ProvisionVariablesStore` (`Sources/cakedlib/PackerLite/ProvisionVariable.swift`) started out as `caker`-only (`Sources/caker/Model/ProvisionVariable.swift`, built for the wizard's "Provisioning variables" editor described in the wizard section below) and were relocated into `CakedLib` with a fully `public` surface specifically so `caked`/`cakectl` could reuse the same store — `caked build`/`caked provision`/`cakectl build`/`cakectl provision` all now call `mutating func validate() throws` (ArgumentParser's own hook) to load `ProvisionVariablesStore.load().asProvisionVarStrings` and **prepend** them to whatever `--var`/`self.provision.vars` the invocation itself supplied — since `BuildOptions.provisionVarsDict`'s dictionary-building `reduce` lets a later array entry overwrite an earlier one for the same key, prepending gives the stored defaults *lower* precedence: an explicit `--var key=value` on the command line always wins over a same-named stored default. `asProvisionVarStrings` validates as it serializes — a key/value containing `=` or `String.grpcSeparator` (`"|"`, used to join multiple `--var` entries for the gRPC wire) is dropped rather than corrupting the wire format; the wizard's own add/edit sheet (`ProvisionVariableNewItemView`) rejects the same characters at input time instead of silently dropping them later, both fixed via Copilot Autofix review on the PR that introduced this. The wizard's `ProvisionVariableDetailView` masks any value whose key contains "password" (case-insensitive) with bullet characters in the compact list row, so a stored secret isn't visible at a glance.

**Vision OCR reliability fix — PNG round-trip required, not a raw `CGImage` capture**: both `PackerLiteDriver.locate(text:)` and `NSView.recognizeText()` (`Sources/cakedlib/VNCLib/VNCVirtualMachineView.swift`) used to hand `VNImageRequestHandler` a `CGImage` captured straight off `imageRepresentation(in:).cgImage` (itself built on `cacheDisplay(in:to:)`, i.e. `-[CALayer renderInContext:]`). Apple documents that path as unsupported/unreliable for GPU-composited layers (Metal, AV, etc.) — and `VZVirtualMachineView`'s framebuffer is exactly that, so the raw capture could come back blank, stale, or partial, causing OCR-based `<locate>`/`<click text=...>` steps to intermittently fail to find text that was genuinely on screen. A plain `CGContext` redraw was tried as a fix and did **not** work — only an actual PNG encode/decode round trip does (`nsImage.pngData` → `VNImageRequestHandler(data:options:)`), which is what both call sites now do, using `NSImage.size` instead of `CGImage` pixel dimensions for the coordinate-scaling math that follows. The PNG-capture step itself was later factored out into a shared `@MainActor func captureImageOCR() -> (pngData: Data, imageSize: CGSize)?` extension on `NSView`, and the view-bounds/scale-factor reads that feed the coordinate math were moved to happen on the main thread *before* the `DispatchQueue.global` dispatch into Vision's own work, rather than inside the background closure — reading `self.bounds` off the main thread there was a genuine data race, not just a style nit (`5bb4d11c`).

`caker`'s VM creation wizard (`Sources/caker/Views/VirtualMachineWizard.swift`) now shows the running VM's live view **inline** — a real embedded VNC connection, not just the raw `VZVirtualMachineView` — in the wizard's own content area while PackerLite provisioning is in progress, instead of requiring a separate debug window. This rides on `PackerLiteEngine.provisioned: [UUID: VirtualMachine]` plus `provisionedStartNotification`/`provisionedTerminatedNotification` (see above): the wizard tracks its own session via a `UUID` `wizardID` (promoted from `String` to match `BuildOptions.identifier`'s type) and matches it against each notification's `userInfo["wizardID"]`. The old separate debug-window path still exists but only under a `DEBUG_PAKERLITE` build flag. The wizard's various VM-related `DispatchQueue`s were also consolidated into one `static let wizardQueue` on `VirtualMachineWizard`. (The VM view's rounded-corner container/clipping mentioned in earlier revisions of this doc was later removed — it didn't suit the VNC-embedded view's own chrome.)

Everything under `Sources/cakedlib/PackerLite/` (driver, engine, resolver, template/`boot_command` parsing, and the resource-bundled `.packerlite.yaml` templates) is part of `CakedLib` itself — there is deliberately **no separate `PackerLite` SPM target**. There was one originally, split out for unit-testability, but it forced `GRPCLib` to depend on it too (for the `--macos-version` CLI option's type), and `CakedLib` already depends on `GRPCLib` — so keeping a shared leaf target meant mirroring an entire extra native target in both Xcode projects (see below) just to avoid one small enum duplication (since resolved a different way — see next). It was folded back into `CakedLib`.

**`MacOSVersion` is no longer duplicated** (it used to be — `GRPCLib` and `CakedLib` each had their own enum, bridged by raw value at the few call sites that needed both). It's now declared **once**, in `GRPCLib` (`Sources/grpc/options/BuildOptions.swift`, still `ExpressibleByArgument` for the CLI), with `CakedLib` adding its template-selection behavior via `extension MacOSVersion { ... }` (`Sources/cakedlib/PackerLite/MacOSVersion.swift`: `bundledTemplateResourceName`, `init?(major:)`, `detect(fromIPSWFilename:)`) rather than declaring a second competing type. `GRPCLib` also gained `MacOSVersion.init?(_ from: Caked_MacOSVersion) throws`, bridging directly from the proto's own `ProvisionRequest.MacOSVersion` enum — needed once provisioning went over gRPC and the wire format needed a `MacOSVersion` too. Since there's only one type now, plain `MacOSVersion` is unambiguous everywhere, including in a file that imports both `GRPCLib` and `CakedLib` — the `GRPCLib.MacOSVersion`/`CakedLib.MacOSVersion` qualification dance from before is gone. (Note: `BuildOptions.swift`'s doc comment above the enum still describes the old two-enum arrangement — it wasn't updated when the duplication was removed, so don't trust it over the code.)

**Stable build-session UUID**: `BuildOptions.identifier: UUID` (`Sources/Grpc/options/BuildOptions.swift`) is generated once per build session and threaded through `VMLocation.tempDirectory(_:runMode:)`, `VMBuilder.buildVM(_:vmName:...)`, and `PackerLiteEngine.provision(id:location:config:template:runMode:progressHandler:)` — so the temp directory name and the provisioning session's `provisioned`/notification tracking (see above) share one caller-controlled identifier instead of each generating its own random UUID independently. `Sources/cakedlib/Handlers/BuildHandler.swift` is the source of that identifier for a real build (`options.identifier`, passed to both `VMLocation.tempDirectory` and `VMBuilder.buildVM`).

**Misc PackerLite/VM-lifecycle fixes worth knowing about**: `VMLocation.waitIPWithLease(config:wait:runMode:startedProcess:)` now takes an already-resolved `CakeConfig` from the caller instead of calling `self.config()` internally — every call site already had one in hand, so this just drops a redundant (and throwing) lookup. `VirtualMachine.swift` gained `async`/`await` overloads of `startVM`/`stopVM` (built on `withCheckedThrowingContinuation`, dispatched onto `vmQueue`) alongside the pre-existing callback-based versions — `PackerLiteEngine`'s build-time orchestrator uses these. The VNC delegate's framebuffer-autoresizing setup, previously gated on `display == .vnc` only, now also covers `display == .none`, so the VM view renders correctly in caker's default/headless display configuration too. `BuildHandler.build(...)` adds a 200ms `Task.sleep` right before invoking the post-build provisioning step, as a settling period to reduce a race between the relocated VM's saved config and Setup Assistant automation starting. Agent installation now logs to `~/install-agent.log` (was `/tmp/install-agent.log`) and ends with a double `sync` call, to reduce the chance of losing writes if the VM is halted right after.

A later, smaller round of fixes in the same area: agent installation's own install script gained a `trap 'sync; sync' EXIT`, on top of the double `sync` call already mentioned above, to flush writes even if the script exits some other way than falling off the end; the temporary install script is now also preserved (not deleted) whenever the log level is debug-or-below, so it's available for inspection after a failed install instead of only ever existing transiently. `CloudImageConverter`'s handling of redirected download URLs moved from one eager `redirectedURL` resolution in `VMBuilder` (done once, up front) to resolving it fresh at each individual download call site — more correct when the same `URL` value gets reused across more than one download operation, since a redirect can be time-sensitive. `VMBuilder`'s ISO branch now derives `config.osName` through `GRPCLib.SupportedPlatform(rawValue:)` before storing it, instead of writing the raw lowercased image-name string directly — so the stored value is always the canonical platform raw value (`fedora`, `centos`, etc.), matching what a later standalone `caked provision` expects to find there, rather than whatever substring happened to be in the ISO's filename. `ProvisionTask`'s pre-boot-command phase now sleeps 10s after the "Starting pre-boot commands" progress step before actually sending anything, giving the VM more time to reach a genuinely ready state first (this is a fixed-delay workaround, not an OCR-`<locate>`-based sync point — worth reconsidering if it turns out to be too short or too long in practice, consistent with this doc's general preference for `<locate>` over blind waits wherever the target screen can be recognized).

A further round: `windowRelativePosition(of:)` (`Sources/cakedlib/VNCLib/VNCVirtualMachineView.swift`) — used to translate an OCR-recognized text's location into a coordinate for the driver's synthesized click — was flipping the Y axis *after* converting from view space to window space instead of before; since a view's own coordinate space and its window's aren't necessarily related by a simple axis flip once other transforms are involved, doing it in the wrong order could land the synthesized click at the wrong point (`43c1746b`). `PackerLiteEngine.provision(id:...)`'s `NSApplication.activationPolicy` handling (set to `.prohibited` for the non-`runInCaker` case, so a headless `caked build --autoinstall`/`caked provision` doesn't steal focus/show a Dock icon) never restored the app's *original* policy once provisioning finished — always leaving it at `.prohibited` — fixed to save and restore it (`f0b78512`). `caker`'s VM window gained a `haveRequestStop` flag so the power button offers "Force stop" immediately once a graceful stop has been requested, instead of only after `status` has already transitioned to `.stopping` — lets an operator escalate to a hard stop without waiting for the graceful shutdown to visibly start.

**Provisioning debug video recording**: `VirtualMachine.swift`'s existing periodic-screenshot pipeline (`kScreenshotPeriodSeconds = 5.0`, the `Timer` started in `startCompletionHandler`, `takeScreenshot()`) already runs for every running VM including during provisioning — it's not gated on `env.provisioning`, unlike communication devices/signal handlers/port-forwarding which explicitly are. This is now reused to record a debug video of a PackerLite provisioning run: `ProvisioningVideoRecorder` (`Sources/cakedlib/PackerLite/ProvisioningVideoRecorder.swift`) wraps `AVFoundation.AVAssetWriter` (`.mp4` file type, `AVVideoCodecType.h264`, `AVVideoProfileLevelH264MainAutoLevel` — deliberately plain, "plays in VLC/QuickTime/a browser/Windows Media Player without extra codecs" rather than optimized for size/quality, so never ProRes or Apple-only HEVC-in-MOV) fed by an `AVAssetWriterInputPixelBufferAdaptor`; each captured `NSImage` is drawn into a `CVPixelBuffer` via a `CGContext` (reusing the existing `NSImage.cgImage` extension in `Sources/Grpc/common.swift`) and appended with a presentation timestamp derived from real wall-clock elapsed time (not an assumed fixed 5s interval), so playback pacing roughly tracks how long provisioning actually took — it's still only ~1 frame per 5 real seconds, intentionally choppy since this is a debug aid, not a screen recording. `init(outputURL:frameSize:) throws`/`append(_:at:)`/`finish(delete:) async` is the whole surface; `finish` tolerates being called with zero frames ever appended (writer session never started) by just removing any partial file instead of calling into `AVAssetWriter.finishWriting`, which requires a session already underway. `VirtualMachineEnvironment` holds the in-flight recorder (`provisioningVideoRecorder`, next to `timer`/`vzMachineWindow`/`provisioning`); `startScreenshotTimer()` starts one — via `VirtualMachine.startProvisioningVideoRecorder()` — only when `env.provisioning == true` **and** screenshots aren't disabled entirely (`refreshScreenshotSettingsCache()`'s existing `enabled` check, i.e. `UserDefaults`'s `NoScreenshot` key — no new opt-out flag was added, this rides entirely on the existing screenshot on/off switch), so ordinary non-provisioning VM runs never pay for it; `takeScreenshot()` feeds the recorder a frame alongside its pre-existing `delegate?.didScreenshot`/PNG-write behavior, unchanged. `VirtualMachine.finishProvisioningVideo(success:) async` finalizes it — `recorder.finish(delete: success)` then clears the stored reference — and must be called explicitly once the overall provisioning outcome is known, since VM teardown itself happens identically on both success and failure and can't be used to infer which occurred. Every path that constructs a `ProvisionedReply` calls it right before doing so: `PackerLiteEngine.provision(id:location:config:template:runMode:progressHandler:)`'s `destroyVM` (the build-time orchestrator) and `CakedLib.ProvisionHandler.provision(...)`'s `destroyVM` (the standalone-provisioning path) — `Sources/caked/Handlers/ProvisionHandler.swift` only forwards progress from the latter and never independently constructs a `ProvisionedReply` itself, so it needed no changes. The standalone path's `ProvisionTask` closure had to drop its `defer { destroyVM(catchableError) }` in favor of an explicit sequential call after the `do`/`catch` — Swift disallows `await` inside a `defer` body, and `finishProvisioningVideo` is async — which is behavior-equivalent here since nothing in the `do` block returns early. `VMLocation.provisioningVideoURL` (mirroring `screenshotURL`) is a fixed `provision.mp4` under `location.rootURL`; the recorder's own `init` removes any leftover file from a previous attempt first, so each provisioning run gets a fresh recording without erroring or appending. No dedicated cleanup was needed for whole-VM deletion — `VMLocation.delete()` already does a directory-level `FileManager.removeItem(at: rootURL)`, not an itemized one, so `provision.mp4` is swept up for free. On failure, `VMLocation.existingProvisioningVideoURL` (non-nil only if the file actually exists — i.e. a recording was actually produced) is used to append the video's path onto the existing failure `reason` string (a new localized format, `"Provisioning failed for VM %@, error: %@. Debug recording saved to %@"` in `Resources/Localizable.xcstrings`) rather than adding a new proto field — it shows up in `caked provision`/`caked build --autoinstall` and `cakectl provision`/`cakectl build --autoinstall` output for free since both already just print `reason`.

**`Bundle.module` gotcha**: `PackerLiteTemplateResolver.swift` reads bundled resources, but `Bundle.module` is only generated by real `swift build`/`swift test` (SPM's per-target codegen). The two hand-mirrored Xcode projects (see below) compile the same file as a plain native target with no such accessor, so the lookup is wrapped in `#if SWIFT_PACKAGE ... #else ...` — keep that structure if you touch resource loading here.

**`caked record` (recording a `boot_command` template by hand instead of writing one)**: writing a `boot_command` template by hand means guessing coordinates and timing, then iterating against a real boot. `caked record <vm> [--output <path>]` (`Sources/caked/Commands/Record.swift`) does the reverse of `PackerLiteDriver`: it boots `<vm>` (built, not yet running — typically created without `--autoinstall`, so it's sitting at its first-boot screen, the same starting state a `boot_command` template is meant to drive), shows it in a local window (`RecordHandler.record(...)`'s `vm.createVirtualMachineView()` + `vm.setupWindow()`, mirroring `ProvisionHandler`'s `display == .none` branch — see below), and records every click/keystroke a human operator performs through that window, writing a ready-to-use `.packerlite.yaml` template to `--output` (default: `VMLocation.recordedTemplateURL`, i.e. `record.packerlite.yaml` under the VM's own storage directory) on `Ctrl-C`. **`caked`-local only for now** — no `cakectl`/gRPC counterpart yet, deliberately mirroring how `caked provision` itself started local-only before later gaining a `cakectl provision` + gRPC `Provision` RPC counterpart (see above); the recording logic itself still lives in `CakedLib` (`RecordHandler`/`ActionRecorder`, not `caked`'s command file) so that follow-up doesn't require restructuring anything.
  - **`VirtualMachine.Mode`**: recording is one of four cases of a unified `VirtualMachine.Mode` enum (`Sources/cakedlib/VirtualMachine.swift`: `.normal`/`.provisioning`/`.recording`/`.recovery`) that replaced two separate, overlapping `Bool` properties (`recoveryMode`/`provisioning`) with no mutual-exclusion guarantee between them. Call sites that used to pass two booleans now pass one `mode:` value (`VMRunHandler`, `VMLocation.startVirtualMachine`); `setupWindow(canHide:)` gained an explicit parameter so a provisioning window can still opt out of hiding on deactivate now that "should this window hide" isn't implied by a boolean anymore; signal handling (`catchUserSignals`) is gated on `sigcaught.isEmpty` rather than a `provisioning` flag, so `.recording` mode inherits the correct "don't install the normal Ctrl-C-exits-immediately handler" behavior automatically instead of needing its own explicit carve-out. The screenshot timer also already special-cased `.provisioning` with a faster interval (`kScreenshotProvisioningPeriodSeconds`, from an earlier PackerLite change) — recording doesn't get its own screenshot cadence, it just needed `Mode` to exist as a real type for `VNCVirtualMachineView`'s tap and the record command's window setup to key off of.
  - **Direct local-window capture, not a VNC-server tap**: an earlier revision of this feature ran `caked record` over the VM's own VNC server, tapping `VNCInputHandler.handlePointerEvent(x:y:buttonMask:)`/`handleKeyEvent(key:isDown:)` (already-translated-from-VNC-protocol values) and displaying the VM through an inline `VNCApp.startVncClient(...)` client window. This was replaced with a direct local-window capture: `VNCVirtualMachineView` (`Sources/cakedlib/VNCLib/VNCVirtualMachineView.swift`) — the `VZVirtualMachineView` subclass `VMView.createView(vm:frame:)`/`vm.createVirtualMachineView()` already return for every local (non-VNC) VM display — now exposes `public var actionRecorder: RecordedActionHandler?`, a pure observer tap called from inside its `mouseDown`/`mouseDragged`/`mouseUp`/`rightMouse*`/`otherMouse*`/`keyDown`/`flagsChanged` overrides with the values resolved straight from the real, native `NSEvent` AppKit already delivered to the view — `event.keyCode`/`event.modifierFlags`/`event.characters`/`event.charactersIgnoringModifiers`, and (for pointer events) `viewRelativePosition(of:)`'s existing top-left-origin conversion, matching the same coordinate space `<click point="X,Y">`/`RecordedAction.pointer` already use elsewhere. No VNC-protocol keysym round-trip, no VNC server, no network port opened at all — the trade-off is that this only works for an operator physically at this host; unlike the VNC-tap approach, a remote VNC client has nothing to attach to. `keyDown`/`flagsChanged`/`scrollWheel` used to be compiled in only under `#if DEBUGEVENT` (pure logging, falling through to Apple's own default handling otherwise) — they're now unconditional overrides (still calling `super` unconditionally, debug logging still gated behind `#if DEBUGEVENT`) specifically so there's somewhere to hook this tap for keyboard input. `flagsChanged` derives `isDown` itself, since AppKit's `NSEvent.modifierFlags` on a `flagsChanged` event reports the *combined* current state (can't distinguish "left shift released, right shift still held" from "left shift still held") — the view instead tracks its own `Set<CGKeyCode>` of currently-held modifier keycodes and toggles per `event.keyCode`, which AppKit does correctly identify per physical key. `RecordHandler.record(...)` arms this tap directly on the view it gets back from `vm.createVirtualMachineView()`, instead of calling `vm.setActionRecorder(_:)` (which still exists, still arms the VNC-server-side tap via `VNCServer.actionRecorder`, unused by `caked record` now but left in place rather than removed). Both taps' callback signature is `RecordedActionHandler = (_ sender: NSView, _ action: RecordedAction) -> Void` — the originating `NSView` is threaded through alongside the action itself so `ActionRecorder` can identify which view produced a given event (needed by the OCR-assisted click feature below, which has to run Vision OCR against *that* view's own rendered content).
  - **OCR-assisted `clickText`/`locate` recording — armed from the toolbar, selected by mouse button**: a "locate mode" toggle button in the recording window's toolbar (`RecordingControls` in `Sources/caked/MainApp.swift`, calling `RecordHandler.Session.toggleLocateMode()` → `ActionRecorder.setLocateModeActive(_:sender:)`) runs Vision OCR (`NSView.recognizeText()`, a new extension added for this — captures the view's current pixel content and runs `VNRecognizeTextRequest` off the main actor at utility priority to avoid QoS inversions, returning each recognized string with its bounding box already flipped from Vision's bottom-left origin into AppKit's top-left convention) against the recording view and draws blue highlight overlays over every recognized text region directly on screen, so the operator can see what's clickable-by-text before clicking. While armed, the **left** mouse button landing inside a highlighted region records `<clickText text='...'>`, and the **right** mouse button on a highlighted region records `<locate text='...'>` — both instead of a raw coordinate-based `<click point="X,Y">`. A left-click outside any highlighted region (or with locate mode off) still falls back to the plain coordinate-based `<click point="X,Y">` token exactly as before; a right-click outside any highlighted region is a pure no-op (unlike the left button there's no coordinate fallback for it, since `<locate>` only makes sense as an OCR anchor and right-click had no recorded meaning at all before this feature existed). `recordPointer` tracks the two buttons as fully independent pending-click states (`pendingClickStart`/`pendingRightClickStart`), so one button's bookkeeping can't disturb the other's. New `Step` cases `clickText`/`locate` are wired through to `PackerLiteTemplate.Command` YAML serialization the same way every other step case already is.
    - **Why a toolbar toggle and not a held modifier**: the first revision of this feature used **Fn held down** as the trigger — simple, but wrong, because Fn is heavily used by genuine macOS accessibility shortcuts an operator legitimately needs to *record*, not suppress (VoiceOver's `<fnOn><f5><fnOff>`, already issued by every bundled macOS template; enabling Full Keyboard Access interactively via Control+F7, which needs Fn+Control+F7 on a modern keyboard since F7 defaults to a media key). A held-key trigger has no way to tell "operator wants the OCR overlay" apart from "operator is toggling VoiceOver" — both are just Fn going down. Moving the trigger to an explicit toolbar button sidesteps the ambiguity entirely: it's UI chrome on `caked`'s own window, never delivered to the VM, so it can never collide with anything the guest needs, now or in the future.
    - **Why mouse button rather than a modifier for the clickText/locate choice**: an earlier revision picked between the two with a held modifier at click time (first Shift, then Option), which needed a matching `recordKey` suppression rule to stop that selector modifier from also being recorded as a real `<xOn>`/`<xOff>` step. Moving the choice to which mouse button was pressed removed the need for that suppression entirely — `recordKey` no longer special-cases anything based on `locateModeActive`, so a modifier held for any reason (VoiceOver's Fn+F5 included) now always records normally, regardless of whether locate mode happens to be armed at that moment.
  - **`ActionRecorder`** (`Sources/cakedlib/PackerLite/ActionRecorder.swift`) accumulates the timestamped `RecordedAction` log (pointer down/up/move + button + x/y; key down/up + keyCode/characters) and turns it into a `boot_command:` YAML document on `finish()`: consecutive printable-character keystrokes with no intervening non-character key/pointer event (and no pause ≥1s, which also breaks a run — otherwise the gap between two characters typed seconds apart could never surface as a `<waitNs>`, since wait-gap insertion only looks at gaps *between* steps) coalesce into one literal `type` line; special/non-printable keys and modifier down/up transitions map to the *existing* named-key token vocabulary in `BootCommand.swift` (`<enter>`, `<tab>`, `F1`–`F20`, `<leftShiftOn>`/`<leftShiftOff>`-style pairs, etc.) via `KeyToken.tokenName`/`ModifierToken.tokenName` (added right next to `parseKey`/`parseToken` in `BootCommand.swift` specifically to stay in sync with the parser) and a `keyTokenForKeyCode`/`modifierTokenForKeyCode` reverse lookup built by *inverting* `PackerLiteDriver.keysym(for:)` (promoted from `private` to `internal static` for exactly this) rather than hand-writing a second keyCode↔token table that could drift out of sync; left-button down→up transitions become coordinate-based `<click point="X,Y">` tokens, or a `<clickText>` token when locate mode's OCR assistance recognized text under the click; a right-button down→up transition on recognized text becomes a `<locate>` token, and is otherwise a no-op (see above); gaps ≥1s between recorded actions become `<waitNs>` steps sized from real elapsed wall-clock time. **This is a first draft, not a robust template** — this codebase has extensively moved *away* from blind waits toward `<locate>` OCR-sync anchors precisely because fixed delays are unreliable (see the "Provisioning debug video recording" and macOS-template-tuning history above), so a recorded template is a good starting point for a human to then harden with `<locate>` anchors, not a finished artifact; both `ActionRecorder`'s own doc comments and `caked record`'s terminal output say so explicitly.
    - **Wait-gap sizing: `<clickText>`/`<locate>` fold the gap into their own `timeout=` instead of a separate blind wait.** Every other step type keeps the plain rule above — a gap ≥1s becomes its own `<waitNs>` block immediately before the step. But `<click text="...">`/`<locate text="...">` already *poll* for the OCR-recognized text to appear (up to a `timeout=` in seconds, `BootCommand.swift`'s `parseClick`/`parseLocate` defaulting it to 10s when the attribute is absent) rather than firing blind, so stacking a fixed `<waitNs>` in front of one is redundant with — and slower than — just letting it poll for the right duration itself. `ActionRecorder.finish()` (via the factored-out `ActionRecorder.commands(for:username:password:)`) special-cases exactly these two `Step` cases: instead of appending a separate `<waitNs>` command, it passes `seconds + 10` (the measured, rounded gap, plus a flat 10s of slack for OCR recognition/rendering latency the raw gap doesn't capture) as an explicit `timeout=` override into `Step.command(username:password:timeout:)`, which threads it onto the emitted `<click text="..." timeout=N>`/`<locate text="..." timeout=N>` token. A gap below the 1s threshold (i.e. one that wouldn't have produced a `<waitNs>` at all under the old rule) still gets no override either, leaving the parser's own 10s default in place. `Step` and `commands(for:username:password:)` are `internal` rather than `private` specifically so `ActionRecorderTests` can construct `.clickText`/`.locate` cases directly and exercise this branching without a real rendered view/Vision OCR pipeline, which a unit test can't practically drive.
  - **`pre_boot_command` routing for non-Darwin VMs**: `ActionRecorder.init(os:username:password:)` now takes a `GRPCLib.VirtualizedOS` (`.darwin`/`.linux`) alongside the account. Linux guests often need early keystrokes (e.g. interrupting GRUB) sent before the installer/boot sequence proper — the same reason `pre_boot_command:` exists in hand-written templates at all (see above). For a non-Darwin recording, `finish()` moves the *first* recorded command block out of `boot_command:` and into its own `pre_boot_command:` field in the emitted YAML; Darwin recordings are unaffected (no `pre_boot_command` field at all, matching every hand-written macOS template). This is a coarse heuristic — it assumes the operator's first distinct action while recording *is* the GRUB-navigation step, not a real semantic split — so a recorded Linux template's `pre_boot_command`/`boot_command` boundary is worth checking by hand, same as everything else about a recorded template being a first draft.
  - **Credential scrubbing is a hard requirement, not optional**: before serializing, any recorded literal text run that exactly matches the VM's own `CakeConfig.configuredUser`/`configuredPassword` (fetched the same way every other provisioning code path does, via `location.config()`) is replaced with the literal placeholders `${var.username}`/`${var.password}` — every bundled template already treats the account as caller-supplied, never hardcoded (see above), so a recorded template baking in the real plaintext password would violate that convention.
  - **Stop-and-save, now via the shared SwiftUI app window with live pause/resume**: recording no longer runs on a bare `NSApplication.shared.run()` loop — `Record.run()` now calls `MainApp.runUI(session.vm, params:, cancellation:)`, the same shared SwiftUI app-window entry point `caked provision --foreground`/`caker` itself use, and delegates save-on-stop into an async completion handler so the VM is fully stopped before the YAML is written. `RecordHandler.Session` gained an explicit `State` (`.stopped`/`.recording`/`.suspended`), `suspend()`/`resume()` methods that arm/disarm the `actionRecorder` tap without tearing down the VM or window, and a `cancel()` entry point satisfying `Cancellable`. `MainWindow`'s toolbar gained a pause/resume control that only appears while `RecordHandler.currentSession` (published as a `static` specifically so the SwiftUI toolbar can observe it without threading a `Session` through every intervening view layer) reports the VM's mode as `.recording` and the session is live: a pulsing "Recording" button (taps to pause → `suspend()`) when live, a hollow "Paused" button (taps to resume → `resume()`) when suspended. `ActionRecorder` gained a matching `reset()` to clear accumulated steps if a session is ever restarted from scratch. `SIGINT` (`Ctrl-C`) remains the required, always-works stop-and-save trigger regardless of pause state — `Record.run()` still cancels `Root.sigintSrc` (`caked`'s default top-level handler, which just force-exits) and installs its own `DispatchSource` the same way `Exec`/`Sh` already do for their own interactive needs, whose handler stops the recorder, writes the YAML to `--output`, prints the output path plus a reminder that it's a first draft, tears the VM down, then terminates. Closing the VM's window as an equivalent trigger was left unimplemented — `Ctrl-C` (or the toolbar, once it's wired to a full stop rather than just pause) always works regardless of window state.
  - Registered statically in `Root.swift`'s `subcommands:` array like every other working command — see the `cakectl provision`/`caked aliases` registration gotchas noted elsewhere in this doc for what happens when that step is missed (compiles cleanly, command silently doesn't exist).
  - **`<voiceOverOn confirm=...>`/`<voiceOverOff>` tokens replace the repeated inline VoiceOver key sequence**: every bundled macOS template used to spell out `<leftAltOn><fnOn><f5><fnOff><leftAltOff><wait5s>` (plus, the first time VoiceOver is ever toggled on a fresh install, a `<locate text='Welcome to VoiceOver'>` + `v` to dismiss the "Use VoiceOver?" confirmation dialog) inline, several times per template. `PackerLiteDriver.voiceOverToggleSequence` (`Sources/cakedlib/PackerLite/PackerLiteDriver.swift`) now encapsulates that exact key sequence — `.modifierOn(.leftAlt)`, `.modifierOn(.function)`, `.press(.function(5))`, `.modifierOff(.function)`, `.modifierOff(.leftAlt)`, `.wait(5.0)` — once, and `voiceOverOn(confirm:title:)`/`voiceOverOff(title:)` replay it, with `voiceOverOn` additionally typing `v` afterward when `confirm: true` is passed (for the one-time confirmation dialog). `BootCommandStep.parse` gained `parseVoideOverOn`/`parseVoideOverOff` (the misspelled "Voide" is an existing internal-only function name, harmless but worth knowing about if you go looking for it) and a `malformedVoiceOverOn` error case; all five macOS templates (`vanilla-macos{12,13,15,26,27}.packerlite.yaml`) were rewritten to use the new tokens instead of the inline sequence. **Bug caught and fixed while syncing this doc**: the newly-added `voiceOverToggleSequence` pressed `.function(2)` (F2) instead of `.function(5)` (F5, the actual VoiceOver shortcut and what every one of the original inline sequences it replaced used) — every recorded/replayed `<voiceOverOn>`/`<voiceOverOff>` would have silently pressed the wrong function key. Fixed to `.function(5)`.
  - **`ActionRecorder` gains matching `voiceOverOn(confirm:)`/`voiceOverOff` `Step` cases and a `toggleVoiceOver(confirm:)` method**, so a human toggling VoiceOver while recording produces the new token instead of the old raw modifier/key steps — `toggleVoiceOver` tracks its own `voiceOverActive` bool internally so alternating calls correctly emit `voiceOverOn` then `voiceOverOff` then `voiceOverOn` again, regardless of what the recorder's `currentModifiers` state happens to be. **A second bug caught and fixed alongside the F5 one**: `Step.command(...)`'s `.voiceOverOn` case emitted `<voiceOverOn confirm="\(confirm)>` — missing the closing `"` before the token's closing `>` — so every recorded template containing a confirmed VoiceOver toggle would have failed to parse back. Fixed to `<voiceOverOn confirm="\(confirm)">`; a new `PackerLiteTests` case (`testVoiceOverOnConfirmAttributeQuotedForm`) locks in that this exact quoted shape round-trips through the parser, alongside new bare-token/attribute-form parse tests for `<voiceOverOn>`/`<voiceOverOff>` generally.
  - **Recording toolbar VoiceOver button** (`RecordingControls` in `Sources/caked/MainApp.swift`): shown only when `showVoiceOver: vm.config.os == .darwin` — VoiceOver toggling is meaningless for a non-macOS recording target, so the button is hidden entirely for Linux VMs rather than shown-but-inert. Plain click calls `session.toggleVoiceOver(confirm: false)`; **Option-click** calls it with `confirm: true`, for the one-time "Use VoiceOver?" dialog. `RecordHandler.Session` mirrors the active/inactive state as a published `isVoiceOverActived` (sic — existing property name, not fixed here since it's a small enough naming slip not worth an unrelated diff) so the toolbar button's icon/help text can reflect it live, and `reset()` clears it back to `false` alongside the existing recorded-steps reset.
  - **Window sizing during recording/provisioning**: `MainWindow`'s `maxWidth`/`maxHeight` are now capped to the VM's actual display dimensions while in `.recording`/`.provisioning` mode (`.infinity` in every other mode) — prevents the window growing larger than the VM's own framebuffer, which would just show empty space beyond the rendered content.
  - **Force-stop option alongside the existing graceful stop**: `MainWindow`'s toolbar Stop button now supports Option-click for an immediate `stopFromUI()` (hard stop) instead of the default `requestStopFromUI()` (graceful ACPI-style shutdown request) — mirroring the same plain-click-vs-Option-click convention the VoiceOver button above just established. The "VM running" quit-confirmation alert gained a second, destructively-styled "Force stop & Quit" button alongside the existing (now explicitly renamed) "Request stop & Quit", so quitting `caked`/`caker` with a VM still running no longer forces a choice between "wait for a graceful shutdown" and "cancel" — force-stop-and-quit is now a first-class third option. French localization strings for both new button labels, plus "Recording"/"Reset" (the recording-toolbar labels from earlier in this section that had been shipping English-only), were added to `Resources/Localizable.xcstrings`.
  - **`Scripts/record.sh`**: a small helper wrapping the manual steps a recording session used to require (delete any existing same-named VM, duplicate the vanilla template, run `caked record` with `--log-level=debug` and the right `--output` path) — replaces hand-configuring the Xcode `record` scheme's arguments/environment before every recording session. The `record` Xcode scheme itself was updated to pass `--log-level=debug` by default.
  - **Progress string is no longer macOS-specific**: `PackerLiteEngine`'s `.step(...)` progress message was `"Provisioning macOS Setup Assistant…"` even for a Linux `boot_command` run, which made no sense once Linux templates existed. Renamed to `"Provisioning Virtual Machine Setup Assistant…"` (localization key renamed to match, `Resources/Localizable.xcstrings`).

### `caker` GUI recording — the same feature as `caked record`, inside the app window

Beyond the CLI, `caker`'s own VM window can record a `boot_command` template too, for a VM already running inside the app (`ConnectionManager.connectionMode == .app`, not external/remote) — no separate `caked record` invocation needed. Lives in the existing `VirtualMachineDocument`/`HostVirtualMachineView` pair (`Sources/caker/Views/VirtualMachine/`), reusing the exact same `VNCVirtualMachineView.actionRecorder` tap and `ActionRecorder` serialization `caked record` itself is built on — no new capture mechanism.

- **`VirtualMachineDocument.canRecord`**: `true` only when `connectionManager.connectionMode == .app && externalRunning == false && virtualMachine != nil` — the same condition under which `HostVirtualMachineView` renders an `InternalVirtualMachineView`, i.e. there's a real local `VNCVirtualMachineView` on screen for the tap to arm against. `HostVirtualMachineView`'s own `canRecord` additionally requires `document.status == .running`, since (unlike `caked record`, which boots the VM itself) this records on top of a VM the user is already driving interactively.
- **`startRecording(output:)`/`stopRecording()`**: arm/disarm an `ActionRecorder` directly on `virtualMachine.vzMachineView` — the already-live rendered view, **not** a fresh `virtualMachine.createVirtualMachineView()` call (see the Copilot-autofix bug below for why that distinction matters). `stopRecording()` serializes via `ActionRecorder.finish()` and writes the YAML to the `NSSavePanel`-chosen output path, showing the same "first draft, harden with `<locate>` anchors" reminder alert `caked record`'s terminal output gives.
- **Toolbar** (`HostVirtualMachineView`'s `recordButton`/`recordingControls`, `ToolbarItemGroup(placement: .primaryAction)`): a Record/Stop button (record.circle icon, `NSSavePanel` prompts for the output path on start), shown next to it while recording is active — the same three controls `caked record`'s CLI `RecordingControls` toolbar offers: a locate-mode ("text recognition") toggle for OCR-assisted `<clickText>`/`<locate>` capture, a Reset button (disabled until at least one action is recorded), and a VoiceOver toggle (plain click = unconfirmed, Option-click = confirmed) shown only for Darwin VMs. `VirtualMachineDocument` mirrors `RecordHandler.Session`'s published state shape (`isLocateModeActive`/`isVoiceOverActived`/`hasRecordedActions`, plain `@Observable` `var`s rather than `@Published`, since `VirtualMachineDocument` is `@Observable` not `ObservableObject`) and forwards `toggleRecordingLocateMode()`/`toggleRecordingVoiceOver(confirm:)`/`resetRecording()` straight into the same `ActionRecorder` APIs (`setLocateModeActive(_:sender:)`, `toggleVoiceOver(confirm:)`, `reset()`) `RecordHandler.Session` already calls. No pause/resume control (unlike the CLI toolbar) — a GUI recording session is stopped-and-saved outright via the Record button rather than paused.
- **Three real bugs caught by Copilot's automated PR review, all fixed via GitHub's "Potential fix" autofix flow** on the PR that introduced this feature (#107):
  1. `startRecording` originally called `self.virtualMachine.createVirtualMachineView()` to get a target view for the tap — but that method **creates a new `VZVirtualMachineView` instance** each call, not the one actually attached to the window and rendering on screen (that's `virtualMachine.vzMachineView`, set once by `CakerVZVirtualMachineView.attachtoDocument`). Arming the tap on a throwaway, never-displayed view would have silently recorded nothing at all. Fixed to guard on `self.virtualMachine?.vzMachineView` instead, with a user-facing alert ("VM view is not ready yet") if it's `nil`.
  2. `startRecording` was missing `@MainActor` despite touching AppKit view state (`targetView.actionRecorder = ...`) and being called from SwiftUI button actions that are themselves main-actor-isolated implicitly — added explicitly.
  3. The "Recording saved" success alert built its message via `String(localized: "Recorded template saved to \(destination.path)\n\n...")` — string interpolation directly inside a `String(localized:)` call, which breaks the point of localization (the interpolated value gets baked into the *key* itself, so the catalog can't have one translated template with a substitution point). Fixed to `String(format: String(localized: "Recorded template saved to %@\n\n..."), destination.path)`.
- **A fourth, unrelated real bug found in the same commit range** (not Copilot-flagged, caught during this doc's own sync pass): the VM shutdown call at the end of a GUI recording session used `vm.stopVM(...)` — the low-level, programmatic stop path — instead of `vm.stopFromUI(...)`, which is what every other UI-initiated stop in `caker` goes through (handles the UI-specific bookkeeping `stopVM` alone doesn't). Fixed in `1b242345`.
- A later PR (#108) added the locate-mode/reset/VoiceOver toolbar controls described above on top of #107's initial plain start/stop toggle — **also caught a real retain cycle via Copilot review**: the tap closure was originally assigned as `targetView.actionRecorder = self.handleRecordedAction` (a bound method reference, which captures `self` strongly in Swift) — since `document → virtualMachine → vzMachineView → actionRecorder closure → document` is a cycle, this would have blocked `VirtualMachineDocument.deinit` from ever running while a recording session was armed, even after the document/window closed. Fixed to `targetView.actionRecorder = { [weak self] sender, action in self?.handleRecordedAction(sender, action) }` via GitHub's Copilot Autofix flow, same as the PR #107 fixes above — this codebase's retain-cycle hunt (see its own section further down) keeps turning up the same "closure/method-reference captures self strongly across an object graph with a cycle in it" shape, worth checking for by default any time a class hands one of its own methods to something it also (transitively) owns.

**Keeping `Caker.xcodeproj`/`CakerAppStore.xcodeproj` in sync**: both projects under `Caker/` hand-duplicate the SPM target graph as native Xcode targets (their own `PBXNativeTarget` per SPM library target, their own file lists, their own `Frameworks` build-phase linkage) rather than consuming `Package.swift` directly — CI/release scripts never touch them (`Scripts/build-signed-*.sh` and the release workflows all use plain `swift build`), but a human opening Xcode does. Since `PackerLite`'s files live inside the existing `CakedLib` native target, adding them there was just new `PBXFileReference`/`PBXBuildFile` entries plus a `Resources` build phase — no new target, no new `Frameworks`-phase linkage anywhere. That's the pattern to prefer: only stand up a brand-new native target (and all the dependency/linkage wiring that requires — see git history around the original `PackerLite` target for what that involved) when a genuinely new, separately-linked SPM library target is unavoidable. The two project files mostly share object UUIDs for common targets, but the App Store variant's `Caker` app target and `VirtualInstallSPI` have different UUIDs/target structure; verify with a scheme-based `xcodebuild -scheme Caker build` (not raw `-target`, which can spuriously fail on unrelated module-map resolution) before assuming a change is complete.

### VM image catalog, `--alias`, and the `aliases` command

`Sources/cakedlib/Resources/VMImages.json` + `Sources/cakedlib/VMImageCatalog.swift` (`VMImageEntry`/`VMImageArchCatalog`/`VMImageCatalog`, both `public`) are the catalog of known VM images — arch-split (`arm64`/`amd64`), category-split (`iso`/`ipsw`/`cloud`), keyed by short ids like `macos12`, `ubuntu2604`, `ubuntu2604Desktop`, `fedora44Server`, `centos9`. This used to live in the `caker` GUI target only (`Sources/caker/VMImageCatalog.swift`, reading `Sources/caker/Resources/VMImages.json`) for the wizard's image picker; it moved into `CakedLib` so `caked`/`cakectl` — which don't depend on `caker` — can resolve catalog ids too, for `build`/`launch`'s `--alias` option (below). `caker` still uses it the same way it always did (`VMImageCatalog.shared`), just via `CakedLib` now. It follows the same `Bundle.module`-vs-Xcode-native-target `#if SWIFT_PACKAGE ... #else ...` dance as `PackerLiteTemplateResolver.swift` (see the "`Bundle.module` gotcha" note above) — reuse that pattern, don't reinvent it, if you touch resource loading here. `<CAKE_HOME>/VMImages.json`, if present, overrides the bundled catalog (see `VMImageCatalog.refreshFromGitHub()`); `VMImageCatalog.githubCatalogURL` points at the file's current repo path and must be kept in sync if the file ever moves again.

`BuildOptions.alias: String?` (`Sources/Grpc/options/BuildOptions.swift`) is a single `@Option(name: .customLong("alias"))` — `caked build --alias macos12 vm` / `caked launch --alias ubuntu2604Desktop vm` — accepting any id from the catalog above, in place of an explicit `--image` URL. (An earlier revision of this generated one boolean `@Flag` per catalog id, e.g. `--macos12`/`--ubuntu2604`, via `Scripts/generate-vm-image-shorthand-flags.py` regenerating `Sources/Grpc/options/VMImageShorthandFlags.swift`; that generated-file/`@OptionGroup` approach was dropped in favor of this one plain `@Option`, since a single string option scales to new catalog ids for free — no regeneration step, no risk of stale flags — where 50+ generated booleans didn't.) `BuildOptions.validate() throws` — `ParsableArguments`'s own zero-argument protocol hook, which ArgumentParser guarantees runs automatically and exactly once on any instance it just decoded (every real `caked build`/`cakectl build`/`launch` invocation and every `BuildOptions.parse([...])`) — copies a non-nil `alias` into `imageId`. It deliberately does *not* live in `BuildOptions.validate(remote:)` (this codebase's own convention, distinct from the protocol, also called manually by `Build`/`Launch`/`Up`): `validate(remote:)` is *also* called on non-CLI-parsed instances — `CakerEnvVM.toBuildOptions(name:)` (`Sources/cakedlib/CakerEnv.swift`, used by `caked`/`cakectl up` for `.cakerenv` files) builds a `BuildOptions` via the `name:diskFormat:...` convenience initializer (which never sets `alias`) and hands it straight to `validate(remote:)` with no real parsing involved, so putting the copy there would be a no-op for that path rather than simply "correctly not applicable."

`BuildOptions.imageId: String?` is the actual value that crosses the `GRPCLib`/`CakedLib` boundary — populated either by `validate()` (from `alias`, for a local `caked build --alias macos12`) or decoded straight off the wire (`Caked_CommonBuildRequest.imageId` → generated Swift property `imageID`, since swift-protobuf capitalizes `Id`/`Url`-style suffixes regardless of the proto field's own casing — for `cakectl build --alias macos12`, which resolves `--alias` to an id client-side during its own parse and sends just the id string). `Sources/grpc/CakedAliases.swift`'s `Caked_CommonBuildRequest.init(buildOptions:)` bridges `imageId` onto the wire the same way it already does for `provisionTemplate`/`provisionVars`/`macosVersion`. `VMBuilder.buildVM`'s `resolveImageId(_:)` (`Sources/cakedlib/VMBuilder.swift`) resolves `imageId` against `VMImageCatalog.shared.resolveShorthand(_:)` into an actual `image` URL/`imageSource` — and, for an `ipsw` hit whose id is also a valid `MacOSVersion` raw value, auto-populates `macosVersion` too — throwing if the id isn't in the catalog at all (which can happen if a newer `cakectl` sends an id this `caked`'s catalog doesn't know yet, or the id was typed by hand rather than copied from `aliases`).

**`caked aliases` / `cakectl aliases`** (`Sources/caked/Commands/Aliases.swift`, `Sources/cakectl/Commands/Aliases.swift`) list every id `--alias` accepts, tagged with its catalog category (`ipsw`/`iso`/`cloud`) — the discoverability story for `--alias` now that there's no `--help` listing of one flag per id. Both are plain local `ParsableCommand`s (no gRPC round trip) reading `VMImageCatalog.shared.aliasEntries` directly, since `cakectl` already depends on `CakedLib` the same as `caked` does — consistent with `--alias` itself only ever crossing the wire as a resolved id string, never a catalog lookup. `VMImageCatalog.aliasEntries` (`Sources/cakedlib/VMImageCatalog.swift`) flattens `current`'s three categories into `[VMImageAliasEntry]` (`id`/`category`/`label`), and `CakeAgentLib.Format`'s generic `renderList<T: Encodable>` (used the same way throughout `Format.swift` for every other `list`-style command) renders it as a table or JSON per `--format`. Like every new `cakectl` command, `Aliases.self` must be added to `Client.swift`'s `subcommands:` array (and `caked`'s to `Root.swift`'s) — see the `cakectl provision` registration gotcha noted elsewhere in this doc; a missing entry compiles cleanly and the command silently doesn't exist.

`VMBuilder.buildVM` resolves `options.imageId` (if set) via `VMImageCatalog.shared.resolveShorthand(id)` (`Sources/cakedlib/VMImageCatalog.swift`) before `options.image`/`options.imageSource` are first used, overriding whatever the `--image` positional argument defaulted to. Resolution checks `ipsw` → `iso` → `cloud`, in that priority order. Every id in the catalog is unique across categories — CentOS/Alpine ship both an installer ISO and a prebuilt cloud image, so their `cloud` entries use a `Cloud`-suffixed id (`centos9Cloud`, `centos10Cloud`, `alpine324Cloud`, `alpine323Cloud`) to stay reachable via `--alias` without colliding with the bare `iso` id. An `ipsw` hit whose id is also a valid `MacOSVersion` raw value (e.g. `macos12`) auto-populates `BuildOptions.macosVersion` if the caller didn't pass `--macos-version` explicitly. `Sources/cakedlib/Handlers/BuildHandler.swift`'s post-build `provision(...)` call uses `VMBuilder.buildVM`'s **returned** `BuildOptions` (not the original pre-resolution one it was given) specifically so provisioning sees the catalog-resolved image/macOS version, not the `--image` default.

### Wizard: provisioning-variables editor

`VirtualMachineWizard.chooseOSImage()`'s "Choose OS" step shows a **Provisioning variables** section (`provisionVariablesSection`, a `@ViewBuilder` computed property) below the ISO/IPSW image picker, for both image sources — an editable list of `${var.<name>}` key/value pairs, the GUI equivalent of repeatable `--var key=value`. Built on the wizard's existing `EditableList`/`EditableListNewItem`/`onEditItem` components (`Sources/caker/Views/EditableList.swift`, `EditableListNewItem.swift`) — the same ones the Sharing/Ports/Sockets steps already use — via three new views modeled directly on `MountView`/`MountDetailView`/`MountNewItemView`: `ProvisionVariablesView`, `ProvisionVariableDetailView`, `ProvisionVariableNewItemView`. `VirtualMachineWizardStateObject.provisionVars: ProvisionVariables` is reset (reloaded from `ProvisionVariablesStore`, not cleared to `[]`) on `init()`/`reset()` and whenever `model.imageSource` changes to `.iso`/a custom image type — a fix (`84f8f113`) narrowed this reload to only the image-source cases where the section is actually shown, since reloading on every switch (including formats that never show the section, like `.qcow2`/`.oci`/`.template`/`.stream`) was pointless churn.

`createVirtualMachine()` sets both `options.provisionTemplate` and `options.provisionVars` directly on the `BuildOptions` value returned by `config.buildOptions(...)` before the build call — **a real, pre-existing bug found while wiring this up**: `model.provisioningTemplate` (the wizard's existing "Provisioning template" file picker for ISO sources) was declared and editable in the UI but never actually applied anywhere — `VirtualMachineConfig.buildOptions(_:imageSource:)` has no knowledge of it, and nothing downstream ever set it on the result either, so a custom provisioning template chosen in the wizard was silently discarded and every GUI `--autoinstall` build used only the auto-detected/built-in template regardless of what was picked. Fixed in the same place the new `provisionVars` needed wiring anyway.

Originally shipped as `caker`-only (`Sources/caker/Model/ProvisionVariable.swift`), then relocated into `CakedLib` and made fully `public` (`9413f9af`) — see "Provisioning variables now persist to `<CAKE_HOME>/ProvisionVariables.json`" above for the resulting `caked`/`cakectl` reuse, the stored-vs-explicit precedence rule, and the `=`/`|` validation. New Swift files added for this feature were initially missing from `Caker.xcodeproj`/`CakerAppStore.xcodeproj` (the usual gotcha — see "Keeping Xcode projects in sync" below) but that gap has since been closed (`b4275e45`).

## Code Organization Conventions

- **Adding a command**: Mirror it in both `Sources/caked/Commands/` and `Sources/cakectl/Commands/` where applicable. Use `ArgumentParser` with `CommandConfiguration` metadata including `abstract:` and `discussion:`.
- **Shared logic**: Put it in `CakedLib` (`Sources/cakedlib/`), not in the executables.
- **gRPC changes**: Edit `service.proto`, regenerate, then update both server (`caked`) and client (`cakectl`/`caker`) sides.
- **Localization**: Use `String(localized: "...")` throughout; localization source files are in `Resources/Localizable.xcstrings`.
- **New SPM library target vs. adding files to an existing one**: a genuinely new, separately-linked target must also be mirrored as a native target in `Caker/Caker.xcodeproj` and `Caker/CakerAppStore.xcodeproj` (new `Frameworks`-phase linkage everywhere its consumers are linked) — prefer adding new files to an existing target instead when possible, since that only needs file references, not a new target; see [PackerLite (unattended OS provisioning)](#packerlite-unattended-os-provisioning) for how to validate either case with a scheme-based `xcodebuild` build.

## Code Style

Swift formatting is enforced by two configs:
- `.swift-format` — used by `swift-format` tool (tabs, 250-char line length, ordered imports)
- `.swiftformat` — used by SwiftFormat (4-space indent width, `--enable indent` only)

Indentation is **tabs** (displayed as 4 spaces). The project uses Swift language mode `.v5` (declared in `Package.swift`).

## CI / Workflows

CI workflows run only on `push` and `workflow_dispatch` events — **never on `pull_request`**. Do not add `pull_request` triggers. Each workflow includes a guard:

```yaml
if: ${{ github.event_name != 'pull_request' && github.event_name != 'pull_request_target' }}
```

Workflows: `release.yaml` (GitHub release + DMG), `appstore-release.yaml` (App Store submission), `publish-wiki.yaml` (wiki → GitHub Pages sync), `sync-docs-from-wiki.yaml` (wiki → `docs/` Jekyll site → GitHub Pages).

## Documentation / Wiki

Wiki source lives in `wiki/` — edit this, not `docs/`. Publish manually:
```bash
GH_TOKEN="${GITHUB_TOKEN}" ./Scripts/publish-wiki.sh <owner> <repo>
```

On push to `main`, `publish-wiki.yaml` syncs `wiki/` to the GitHub wiki, and `sync-docs-from-wiki.yaml` regenerates the Jekyll site under `docs/` (published at `caker.aldunelabs.com`) from it. `docs/` is generated output — changes there are overwritten by the sync.
